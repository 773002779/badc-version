## 1. 设计目标与硬约束

### 1.1 目标

| # | 目标 | 技术落点 |
|---|---|---|
| G1 | 发布进度一屏可见、状态可信 | 单实例状态机 + 事件驱动推进 + 外部系统对账 |
| G2 | 检查与部署并行，门禁不阻塞测试 | 门禁维度与主状态解耦，检查异步采集、实时回写 |
| G3 | 生产发布五道闸不可绕过 | 服务端准入判定 + 快照 + 执行前复核，前端只做展示 |
| G4 | 一个卡住的流水线不能锁死后继 | 锁带 TTL + DB 唯一约束兜底 + 管理员强拆 |
| G5 | 外部系统状态不丢、不假成功 | Webhook 优先 + 定时对账 + 幂等键 |
| G6 | 构建部署引擎可替换 | `CicdEngine` SPI，一期仅 CODING 实现 |
| G7 | 多部署单元共库不互相作废门禁 | commit 按模块路径过滤 + 镜像 digest 绑定 |

### 1.2 硬约束（来自需求）

1. **构建只执行一次**，测试与生产共用同一镜像；生产部署前强校验镜像 digest 一致，不一致阻断且不可豁免（C23/J27）。
2. **一期只回滚镜像**，不自动回退代码（C17/C25）。
3. **分支不落平台**：只读自 CODING 任务，不创建、不编辑、不校验（C21）。
4. **一期无合并动作**：生产部署成功即「已完成」（C25）。
5. **门禁按最高缺陷等级判定**，非逐项独立（C12）。
6. **生产窗口按「所选计划生产时间」判定**，非提交瞬间（C22/J5）。
7. **封板只拦生产、拦而不拒**，在途发布自动转双签（C8）。
8. **运维/运维组长不得发起代码版本变更**（C20）。

**模块边界规则**（用 ArchUnit 在 CI 中强制）：
- `web` 只能依赖 `application`；
- `application` 可依赖 `domain` 与 `infra` 暴露的接口；
- `domain` **不得**依赖 `infra`（引擎与通知通过端口接口反向注入）；
- 跨模块禁止直接访问对方 Mapper，必须经应用服务。

## 3. 领域模型与状态机

### 3.1 聚合与边界

| 聚合根 | 内部实体 | 一致性边界 |
|---|---|---|
| `ReleaseTask` | 任务基本信息、成员 | 任务与成员同事务 |
| `ReleaseItem` | 变更项、门禁维度、基准 commit | 变更项状态与门禁状态同事务 |
| `ReleaseOrder` | 发布单、OA 工单、准入快照 | 发布单与其快照同事务 |
| `PipelineInstance` | 节点、节点任务 | 实例创建时预生成全部节点与任务 |
| `CheckResult` | 单次检查结果 | 结果写入幂等（按 checkKey） |
| `Waiver` | 豁免单 | — |
| `FreezeEvent` | 封板 | — |
| `Approval` | 审批单、会签记录 | — |
| `DeployUnit` | 环境 DE、CODING 任务绑定 | 单元配置同事务 |

**跨聚合只经领域事件与 ID 引用**，不做跨聚合事务。例：节点任务完成 → 发布 `NodeTaskCompletedEvent` → `PipelineOrchestrator` 在独立事务中推进实例。

**任务进度**：`完成率 = count(status=DONE) / count(* items)`，实时计算并缓存 5s；「有阻塞」标记由 `count(status ∈ {TESTING, GATE_PENDING, SUBMITTED, PENDING_APPROVAL, READY}) > 0` 派生，不落库（J9）。

### 3.2 主状态机

`ReleaseItemStatus`（持久化字段）

```
PENDING(待发布)
  → BUILDING(发布中-构建) → TESTING(测试中) → GATE_PENDING(待生产准入)
  → SUBMITTED(待提交) → PENDING_APPROVAL(待审批) → READY(待执行)
  → PROD_DEPLOYING(发布中-生产) → DONE(已完成)
终态/旁支：GATE_FAILED(门禁未通过) FAILED(失败) REJECTED(已驳回)
          CLOSED(已关闭) TERMINATED(已终止) ROLLED_BACK(已回滚)
```

**迁移矩阵**（`ItemStateMachine` 以 `Map<Status, Map<Event, Status>>` 静态定义，非法迁移抛 `IllegalTransitionException`）

| 当前 | 事件 | 目标 | 触发方 |
|---|---|---|---|
| PENDING | PUBLISH | BUILDING | 用户点发布 |
| BUILDING | BUILD_OK | TESTING | 引擎回调 |
| BUILDING | FAIL | FAILED | 引擎回调 |
| TESTING | GATE_PASS | GATE_PENDING | 门禁通过 |
| TESTING | GATE_FAIL | GATE_FAILED | 门禁未通过 |
| TESTING | TEST_DEPLOY_FAIL | FAILED | 引擎回调 |
| GATE_PENDING | SUBMIT | SUBMITTED | 开发提交生产发布 |
| GATE_PENDING | CHECK_INVALID / TEST_REVOKE | GATE_FAILED | 门禁/用户 |
| SUBMITTED | NEED_APPROVAL | PENDING_APPROVAL | 准入引擎 |
| SUBMITTED | CHECK_INVALID | GATE_FAILED | 门禁失效 |
| SUBMITTED | FREEZE_HIT | PENDING_APPROVAL | 封板判定 |
| SUBMITTED | NO_APPROVAL | READY | 准入引擎 |
| PENDING_APPROVAL | APPROVE_ALL | READY | 审批完成 |
| PENDING_APPROVAL | REJECT | REJECTED | 审批人 |
| PENDING_APPROVAL | GATE_INVALID | GATE_FAILED | 快照复核 |
| READY | EXECUTE | PROD_DEPLOYING | 运维 |
| READY | CHECK_INVALID | GATE_FAILED | 门禁失效 |
| READY | FREEZE_HIT | PENDING_APPROVAL | 封板在途 |
| PROD_DEPLOYING | PROD_OK | DONE | 引擎回调 |
| PROD_DEPLOYING | PROD_FAIL | FAILED | 引擎回调 |
| GATE_FAILED / FAILED | RERUN | TESTING | 重新发布（从失败节点） |
| GATE_FAILED / FAILED | RERUN_FULL | BUILDING | 重新发布（commit 变化，全量） |
| REJECTED | RESUBMIT | SUBMITTED | 重新提交 |
| 任意非终态 | CLOSE | CLOSED | owner/管理员 |
| 任意非终态 | EXIT | TERMINATED | 用户退出流水线 |
| DONE | ROLLBACK | ROLLED_BACK | 回滚完成 |

**设计要点**
- `GATE_PENDING` 只在**两门禁都满足**时进入；「测试过了但检查没过」仍停留在 `TESTING`（这也是需求审阅指出的缺口，用门禁维度表达）。
- `SUBMITTED` 是显式「已提交、尚未判定审批链」的瞬态，服务在同一事务内推进到下一状态，主要用于审计留痕。
- `DONE` 是终态；一期无 MR 环节，因此不存在「已发布未合并」的中间态。
- **二方库（`type=LIB`）走独立编排**：构建 → 安全检测 → 制品入库，不经测试部署/生产部署/审批；入库成功即 `DONE`，计入完成率（C13/FR-P-09）。

### 3.3 门禁维度

两道门**正交**，各用一列（P2 / V19 修正：早期把两者放在 `release_item.gate_status` 一列里，
记录检查结果时会覆盖掉「测试不通过」，属于建模错误）：

| 列 | 值 | 写入方 |
|---|---|---|
| `gate_status`（检查） | `CHECK_RUNNING / CHECK_PASS / CHECK_WAIVED / CHECK_FAIL / CHECK_INVALID` | `GateService.evaluate` |
| `test_status`（测试） | `TEST_PENDING / TEST_PASS / TEST_FAIL / TEST_REVOKED` | 测试人员的通过/不通过/撤回 |

- 检查维度由 `GateEvaluator` 从 `gate_check` 行 + 生效豁免算出，不看主状态；
- 测试维度记录「谁、何时、为什么」，`last_test_pass_by/at` 存通过人，`test_fail_reason` 存不通过原因；
- UI 分列展示；主状态只表达「走到哪一步」。

### 3.4 准入快照

提交生产发布时生成不可变快照 `GateSnapshot`：

```json
{

  "publishNo": "624442",
  "plannedReleaseTime": "2026-11-25T22:30:00+08:00",
  "inWindow": true,
  "windowRuleId": 12,
  "frozen": false,
  "freezeIds": [],

  "checkConclusion": "WAIVED",
  "waiverIds": ["WV-0007"],
  "testConclusion": "PASS",

```

### 4.3 并发控制

| 场景 | 手段 |
|---|---|
| 变更项状态迁移 | `UPDATE ... WHERE id=? AND row_version=?`，失败重试 3 次后放弃并告警 |
| 节点推进 | Redis 锁 `lock:pipe:{instanceId}` + 状态前置校验（CAS） |
| 单元互斥 | Redisson 可重入锁 `lock:unit:{unitId}`，TTL 4h + 看门狗续期 + DB 唯一约束 |

| 外部触发重复 | `node_task.uk_idem` 唯一键，重复插入捕获 `DuplicateKeyException` 视为幂等命中 |

## 5. 流水线执行引擎

### 5.1 数据模型与生命周期

- 实例创建时按 `exec_type` 预生成节点（**在线 4 个 / 日常 2 个**）与其下 `node_task`：
  - `BUILD`：`CODE_CHECK`、`PKG_BUILD`、`IMG_BUILD`；
  - `TEST_DEPLOY`：每个测试 DE 一个 `DEPLOY` 任务；
  - `VERIFY`：按检查项生成 `CHECK` 任务（每项一条，结果落 `check_result`）；
  - `PROD_DEPLOY`：每个批次 × 每个 DE 一个 `DEPLOY` 任务；
  - `DAILY_DEPLOY`（仅日常实例）：每个日常 DE 一个 `DEPLOY` 任务；
  - **二方库实例（`type=LIB`）**：`LIB_BUILD`（PKG_BUILD）→ `LIB_SECURITY`（CHECK）→ `LIB_PUBLISH`（制品入库），共 3 个节点。
- `node_task.status ∈ {PENDING, RUNNING, WAITING_EXTERNAL, SUCCESS, FAILED, TIMEOUT, SKIPPED}`。
- 长耗时的外部任务统一为 `WAITING_EXTERNAL` + `external_id`，等待回调或对账。

**日常实例与在线实例的差异**：日常发布不生成 `release_order`、不参与门禁与审批、不占用单元锁、**不改变变更项主状态**，只写 `pipeline_instance(exec_type=DAILY)` 与节点记录，供开发自查（C10/C24）。

### 5.2 推进模型（事件驱动 + 轮询兜底）

```
引擎回调(webhook) ─┐
定时对账(30s)     ─┼─▶ NodeTaskCompletionService
超时扫描(30s)     ─┘        │
                            ▼
                 ┌─────────────────────────┐
                 │ PipelineOrchestrator     │
                 │ · 加实例锁              │
                 │ · 同节点任务是否全完成？ │
                 │ · 完成 → 推进下一节点   │
                 │ · 失败 → 实例失败/暂停  │
                 └─────────────────────────┘
                            │
                            ▼
                 发布领域事件（NodeCompleted / NodeFailed / InstanceFinished）
                            │
          ┌─────────────────┼──────────────────┐
          ▼                 ▼                  ▼
    门禁重算         变更项状态迁移        通知/审计
```

**关键规则**
1. **同一实例同一时刻只有一个推进者**：`lock:pipe:{instanceId}`，未获锁直接返回。
2. **节点完成判定**：该节点下所有非 `SKIPPED` 任务均为 `SUCCESS`。生产部署节点额外要求所有批次成功。
3. **失败即停**：任一任务 `FAILED/TIMEOUT` → 实例 `FAILED`，同节点其余 `PENDING` 任务置 `SKIPPED`；生产批次失败时**已成功批次保留**（J8）。
4. **门禁不等节点**：`CHECK` 类任务不阻塞 `VERIFY` 节点完成，结果异步回写 `check_result` 并触发 `GateEvaluator`。

### 5.3 重新发布（C15）

```java
public RerunPlan decideRerun(ReleaseItem item, String headSha) {
    boolean changed = !Objects.equals(item.getBaseCommit(), headSha)
                   || !Objects.equals(item.getLastBuildSha(), headSha);
    if (!changed) {
        return RerunPlan.fromFailedNode(item);      // 复用镜像与镜像级检查
    }
    return RerunPlan.full();                        // 全量重来 + 作废测试通过
}
```

- commit 比对**按模块路径过滤**：`git log --since base -- <modulePath>` 无提交即视为未变（J18）。
- 未配置 `module_path` 时降级为整库比对，并在返回体带 `degraded=true`，前端提示风险。
- `RerunPlan.fromFailedNode`：复用 `pipeline_instance.image_digest`，跳过 `BUILD` 与镜像级检查，从失败节点开始新建实例。
- 全量重来：`REVOKE_TEST_PASS`（需二次确认，记录操作人）。

### 5.4 超时与重试

| 项 | 策略 |
|---|---|
| 构建超时 | `deadline_at = start + 60min`（可配），超时置 `TIMEOUT` 并调引擎取消 |
| 部署超时 | 默认 8min（原型口径），按 DE 可配 |
| 外部调用超时 | 连接 5s / 读 30s；失败重试 3 次（指数退避 1s/3s/9s） |

| 任务重试 | 用户手动「重试」→ `attempt+1` 新建任务行，旧行保留 |

## 7. 门禁引擎

> **P2 落地修正（已实现，v1.1）**：本节描述的是实现形态，不是最初草案。
> 关键差异：检查结果落 `gate_check`（唯一键 `(item_id, check_kind, stage)`，重复回传是覆盖不是新增）；
> 升到 `VERIFY` 节点时一次性触发七项检查（草案的「构建成功即触发镜像级检查」属提前优化，P2 未做）；
> 判定用**最高等级**而不是逐项 pass/fail；只有中危可豁免；检查未完成一律不算通过。

### 7.1 采集时机

| 阶段 | 触发点 | 检查项 |
|---|---|---|
| 镜像级 | `VERIFY` 节点进入时（测试部署成功后） | Sonar、组件漏洞、架构规范、版本缺陷 |
| 环境级 | 同上 | 安全动态测试、自动化测试、数据库规范 |

- 结果幂等键：`(item_id, check_kind, stage)`，重复上报覆盖更新（取最新完成时间与 `attempt`）。
- 检查结果是**外部系统异步返回**：`check.start` / `check.env.start` 触发，30s 轮询
  `check.query`；引擎不可达或返回无法判定的状态 → `UNKNOWN`，门禁读作「检查中」，下一轮重试。
- 单项超时 30 分钟判 `TIMEOUT`（D6），门禁记未通过。
- 结果存证：等级、问题数、报告链接、扫描对象（commit / 镜像 digest / DE）。

### 7.2 判定算法

```java
// GateEvaluator.evaluate(checks, waiver, now, commitSha, digest)
if (checks.isEmpty())                          return RUNNING;   // 从未开始
if (anyCheck(INVALID))                         return INVALID;   // 提交/镜像变化、豁免到期
if (anyCheck(PENDING|RUNNING|UNKNOWN))         return RUNNING;   // 未完成 ≠ 通过
blocking = checks.where(severity.blocks() && status != INVALID)   // 高危/严重/中危
if (blocking.isEmpty())                        return PASS;
if (anyBlocking().severity !in (S2))           return BLOCK(waivable=false);  // 高危/严重不可豁免
if (waiver.countsAt(now, commitSha, digest))   return WAIVED;     // 已批准 + 未到期 + 同一快照
                                               return BLOCK(waivable=true);
```

- **最高等级决定结论**（MECE 口径）：一个检查报 `PASS` 但等级是 S1，仍然阻断——等级是事实，
  引擎的状态词只是它的意见。
- 判定结果写回 `release_item.gate_status`；主状态只在**终局**时推进：
  - `TESTING` 且两道门都满足 → `GATE_PASS`（→ 待生产准入）；
  - `TESTING` 且出现**不可挽回**的结论（INVALID、不可豁免的 BLOCK、测试不通过/撤回）→ `GATE_FAIL`；
  - 中危阻断**不**结束变更项：停在测试中，等豁免决定，避免「一有中危就得重跑」。
  - 已准入（`GATE_PENDING/SUBMITTED/PENDING_APPROVAL/READY`）后结论变差 → `CHECK_INVALID` /
    `TEST_REVOKE` / `GATE_INVALID`，回到门禁未通过（C16）。
- **豁免不参与测试门禁**：`WAIVED` 只解检查，测试仍需 `TEST_PASS`。

### 7.3 豁免失效

| 变化 | 处理 |
|---|---|
| commit 变化 / 全量重跑 | `gate_check` 全量置 `INVALID`，豁免随快照失效 |
| 镜像 digest 变化 | 同上（比较 `scanned_object` 与当前 digest） |
| 到期 | 每日 00:05 扫描 → `EXPIRED` + 检查结果置 `INVALID` + 重算门禁 |
| 新增 S0/S1 | 豁免不覆盖，直接 `BLOCK`（申请接口直接拒绝） |

- 一张豁免单覆盖「发布单 + 中危检查项集合 + commit/镜像快照」，有效期最长 90 天；
- 申请人是任务成员即可，**审批需 `gate:waive`（管理员/运维组长）且不能自审**（40008）。

### 8.1 窗口计算

```java
public WindowCheckResult check(long subsystemId, LocalDateTime planned) {
    ZoneId zone = window.getTimezone();
    // 1. 例外日历优先
    var ex = exceptionRepo.find(window.getId(), planned.toLocalDate());
    if (ex != null && ex.getMode() == CLOSED) return OUT;
    if (ex != null && ex.getMode() == OPEN) return IN;   // 临时开放

    // 2. 星期规则
    int dow = planned.getDayOfWeek().getValue();
    for (WindowRule r : rules.get(dow)) {
        if (r.covers(planned.toLocalTime())) return IN;   // end<start 时按跨零点判定
    }
    return OUT;
}
```

- **跨零点**：`22:00–02:00` 覆盖 `22:00~23:59` 与 `00:00~02:00` 两段，且**不应**匹配次日 `01:00` 的「日归属」歧义——实现上以「时间点落入区间」为准，不做日期归属拆分。
- 返回 `nextWindow`（未来 7 天内最近可用区间）供前端「改期」提示。
- 判定结果写 `release_order.window_result`，供审计。

### 8.2 封板判定与在途处理

```java
public List<FreezeEvent> activeFreezes(long subsystemId, Instant at) {
    return repo.findActive(at).stream()
        .filter(f -> f.getScope() == GLOBAL || f.getSubsystemId() == subsystemId)
        .toList();
}
```

**生效时**（`FreezeAppService.activate`）：
1. 写 `freeze_event`；
2. 查受影响发布单：`status IN (SUBMITTED, PENDING_APPROVAL, READY, PROD_DEPLOYING)` 且同系统；
3. 对 `SUBMITTED / PENDING_APPROVAL / READY`：补双签（若已有单签则追加上级会签），状态转 `PENDING_APPROVAL`；
4. 对 `PROD_DEPLOYING`：**不打断已上线批次**，置「已暂停」标记，运维决定继续/停止（C16）；
5. 企微机器人通知（见第 10 章）。

**解除时**：重新计算准入；已完成的会签意见保留，缺失环节补齐（J19）。

### 8.3 审批链生成

```java
public ApprovalChain build(GateSnapshot snap, long subsystemId) {
    if (snap.isFrozen())                     return chain(OPS_LEAD, DEPT_MANAGER);
    if (snap.getWindowResult() == OUT)       return chain(OPS_LEAD);
    return ApprovalChain.empty();            // 免审批 → READY
}
```

- **顺序会签**（J7）：前一位通过才流转下一位；驳回即终止。
- **自审批拦截**（C20）：`signer == submitter` → 取配置的代理人；无代理 → 上级；均无 → 阻断并提示「请配置代理」。
- 超时：`sla = 12h` 提醒，`24h` 升级（发给上一级 + 管理员）。

### 8.4 执行前复核

```java
public ReviewResult review(long orderId, long operatorId) {
    GateSnapshot snap = snapshotRepo.latest(orderId);
    ReviewResult r = new ReviewResult();
    // ① 封板是否变化
    r.setFrozen(!activeFreezes(unit.subsystemId, now()).isEmpty());

```

- `digestMatched == false` → **硬阻断，不可豁免**（J27）。
- 复核结果写 `audit_log`，执行按钮产生 `execute_attempt` 留痕。

### 8.5 回滚（一期仅镜像）

**版本来源**
- 以 `(unit_id, image_digest, deploy_batch_no)` 归档成功部署记录；
- `GET /units/{id}/rollback-versions` 返回「当前线上版本 + 近 10 个历史版本」，字段含分支模式、流水线模式、基线版本、发布单号、发布完成时间、发布人、成功发布的环境、更新内容。

**执行流程**
1. 校验单元锁未被他实例持有；
2. 创建 `rollback_record` + `pipeline_instance(trigger_type=ROLLBACK, exec_type=ONLINE)`；
3. 节点仅 `PROD_DEPLOY`，按 `deploy_batch_no` **反向批次**串行（蓝绿 → 容灾 → 生产，顺序可配）；
4. 调用**生产部署任务**，传入目标镜像 tag/digest；
5. 全部成功 → `release_order.status = ROLLED_BACK`，变更项 `ROLLED_BACK`。

**约束**
- 免审批、不受窗口限制，但**强制填写原因**（J13）；
- 封板期提示但不阻断；
- 占用同一把单元锁，回滚期间禁止并发上线发布。

**一期的一致性缺口（必须显式提示）**
平台只回滚镜像，`release_order` 置 `ROLLED_BACK` 但**不回写分支或基线**。页面需持久展示：「线上已回滚至 {tag}（commit {sha}），**代码分支未回退，请人工 revert**」。二期引入 revert MR 后移除该提示（C17/C25）。

### 8.6 实现对照（P3，2026-11-23）

**判定用两个谓词，各管一件事**

- `active(at)`（生效中）：`ACTIVE AND start_at <= at AND end_at > at`。用于横幅、执行前复核、批次边界探针。
- `governsAt(now, plannedAt)`（治理）：`ACTIVE AND end_at > now AND start_at <= max(now, plannedAt)`。
  用于准入判定与在途处理——「下周封板」对「下周计划发布」今天就生效（fail-closed），
  避免执行前才发现要补签。
- 执行前复核刻意用 `active`：被 `governing` 提前要求过的签名已在准入时收齐，若复核按 `governing`
  判定，会把「计划在封板开始前完成」的发布单挡在执行之外。

**审批链**（`admission_snapshot` 维度，见 V22）

| 场景 | 链 |
|---|---|
| 窗口内、无封板 | 空（免审） |
| 窗口外、无封板 | `OPS_LEAD` |
| 封板（无论窗口内外） | `OPS_LEAD` → `DEPT_MANAGER` |

- 步骤按角色，不按人；提交人不得签自己的单（40008），不自动转交（转交/代理未做）。
- 一条链只属于一个快照；重新提交产生新快照，旧链保留为历史（唯一键 `(snapshot_id, step_no)`）。
- 并发：`ensureChain` / `dropPending` 先锁 `release_order` 行（`SELECT … FOR UPDATE`），
  MySQL `REPEATABLE READ` 下普通重读看不见并发提交。

**在途处理与重算**

- 声明封板时：对 `governsAt` 命中且快照未记录该封板的发布单，按顺序补
  `OPS_LEAD`、`DEPT_MANAGER`（缺哪个补哪个，步号保持签名顺序），`READY`/`SUBMITTED`
  拉回 `PENDING_APPROVAL`；若快照已记录（已签过）或两签都已是 `APPROVED`，不补也不降级——
  否则会留下「待审批但无待签步骤」的死局，新封板改为在执行前复核处拦截
  （40002 载荷带 `signaturesAlreadyGiven`，页面据此说明无需再签）。
- 解除/到期：仅当「已无任何封板治理该发布单」时，按快照 `in_window` 决定丢哪些待签步骤
  （窗口内丢 `OPS_LEAD` + `DEPT_MANAGER`；窗口外只丢 `DEPT_MANAGER`），已签批注保留；
  链因此完整则 `APPROVE_ALL → READY`。多张封板并存时，另一张仍治理则该步骤保留。
- 扫描有界：每轮按 `id` 键集分页，200/页 × 10 页封顶，超出记 WARN；未处理的单在准入/复核
  仍会按封板表拦截。

**生产批次执行**

- 提交/执行前按 `env_de.deploy_batch_no` 为每个 DE 生成 `PROD_DEPLOY` 任务（批号落库），
  执行只触发「最小未完成批次」，批内并行、批间串行。
- 触发前原子领取任务（`PENDING → RUNNING`，`attempt+1`），并发推进不会重复触发同一个 DE。
  领取同时写入 15 分钟「触发宽限」deadline：进程若在调用引擎前退出，reconcile 会对
  `RUNNING` 且无 `external_id`、deadline 已过的任务置 `TIMEOUT`，走正常失败路径（实例/节点
  `FAILED`），运维可重跑，而不是留下永远 `RUNNING`、任何入口都不接受的实例。
- 批次边界探针在每批结束后检查：新封板生效、不可豁免的门禁阻断、实例已非执行态 →
  暂停实例并写 `status_reason`，等待运维「继续」（复核通过才恢复）。
- 60s 单元租约续期任务延长 `RUNNING/PAUSED` 实例的锁；执行入口在锁已失效时给 40006
  要求重新发布，而不是让流水线在推进中失败。`PAUSED` 的续租有上限
  （`release.unit-lease.max-paused-hours`，默认 168h）：被驳回且无人重提、或长期无人处理的
  暂停单不会永久占住部署单元，超时后四小时租约自然过期，单元可被新的发布获取
  （该单再执行时按 40006 走重新发布）。
- 生产重跑（`RERUN_FROM_NODE` 停在 `PROD_DEPLOY`）用 `EXECUTE_RERUN`
  （`TESTING → PROD_DEPLOYING`），复用镜像与准入，不再走一轮审批。

**复核与错误码**

- 只比对「变了什么」：封板是否生效、豁免是否仍有效、实例镜像 digest 与快照是否一致；
  不重算窗口。
- digest 不一致 → 40007 硬阻断（不可豁免）；封板/豁免失效 → 40002（附 `review` 与原因）；
  锁失效 → 40006。
- `/releases/{publishNo}/resume` 拒绝生产暂停（必须走 `control:execute-prod` + 复核），
  避免绕过执行前复核。

**与设计稿不一致的地方（代码为准）**

1. **版本清单不落归档表**。设计 §8.5 写「以 `(unit_id, image_digest, deploy_batch_no)` 归档成功部署记录」；
   实现每次从 `node_task` 现算，`rollback_record` 只存回滚本身。批次数是
   `COUNT(DISTINCT node_task.target_id)`——该 digest 历史上成功部署过的生产 DE 数，跨发布单汇总，
   页面标注为「批次数」；环境由 `node_task.target_id → env_de.env_kind` 去重聚合。设计 §8.5 草案
   列出的「分支模式 / 流水线模式 / 基线版本 / 更新内容」**未返回**：版本只有
   `digest / finishedAt / publishNo / executedBy / batchCount / environments`。
2. **当前版本必须有来源发布单**。设计写「取来源发布单（可能为空）」；实现不允许为空：发布单、
   变更项缺失，或变更项不是 `UNIT`，都报 40001——`pipeline_instance.order_id` 不能空。
3. **V25 的真实内容**：`release_order.executed_by VARCHAR(32) NULL` + `rollback_record`（`unit_id /
   instance_id / pipeline_no / source_* / target_* / reason / requested_by / status /
   failure_reason / created_at / finished_at`，索引 `idx_rollback_unit(unit_id, created_at)` 与
   `idx_rollback_instance(instance_id)`）。`executed_by` 由 `ExecuteProdService.syncOrderStatus` 在
   每次执行/恢复/重跑时写，历史行为空、页面显示 `—`，不进发布单聚合。
4. **自动启动受配置控制**。`RollbackService` 读 `release.pipeline.auto-start`（默认 true）；关闭时
   实例停在 `PENDING`，由 reconcile 进首节点（测试就是关掉它自己驱动实例）。设计 §5 只写了
   「事务后 `advancer.advance`」。
5. **完成回写是监听器，不是补偿表**。`InstanceFinishedEvent` 是普通 `@EventListener` +
   `@Transactional`，在流水线推进事务里收敛；`PAUSED / CLOSED / TERMINATED` 不收敛，记录保持
   `RUNNING`（被放弃的回滚在页面上如实显示「执行中」）。
6. **全局记录页只列发布单**。回滚不建单（R41），`GET /api/v1/releases` 里没有回滚行，回滚只能从
   `GET /api/v1/rollbacks` 看到。筛选比设计 §4 多一个 `unitId`；`systemId` 在服务里叫
   `subsystemId`，是同一列。

## 12. 接口设计

### 12.1 约定

- 前缀 `/api/v1`；统一响应 `{code, message, data, traceId}`。
- 分页 `?page=1&size=20`，返回 `{total, list}`。
- 幂等：写操作接受 `Idempotency-Key` 头，Redis 存 24h。

**与草案的差异（已记录在台账）**

1. 草案用 `/releases/{publishNo}/test-pass` 与 `/gates`；实现按**变更项**聚合（`/items/{itemId}/gate/*`），

3. 准入不足的拒绝码用 **40002 `GATE_BLOCKED`**（错误码表里本就有「门禁未通过」），不是 40011：

#### 12.2.2 CODING 对接配置（随 P2 之后落地）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/coding/conn` | 全局连接；未配置时返回 `configured:false`，不是错误 | `setting:manage` |
| PUT | `/api/v1/coding/conn` | 保存地址 / 团队 / 默认项目 / 凭证；`token` 为空即保留原凭证 | `setting:manage` |
| POST | `/api/v1/coding/conn/test` | 测试连接；body 可选（草稿测试），缺省字段回落到已存配置 | `setting:manage` |

- **测试连接做什么**：用给定连接调用 `job.list`（BUILD 再 DEPLOY），一次调用同时证明地址可达、凭证有效、
  项目可达；响应带 `buildJobs / deployJobs`。失败时原样返回引擎消息（引擎已脱敏），不把「地址 / 凭证 /
  项目」硬拆成三行去猜——引擎只给一句话（`HTTP 401`、连接超时、响应不是数组），拆行会变成编造。
- **凭证**：AES-GCM 加密落库，接口只回 `tokenHint`（`tok-***`）；轮换 = 填新值，留空 = 保留。
  `V20__coding_probe.sql` 记录最近一次校验（时间 / 成败 / 消息），页面据此显示「上次校验」。
- **默认项目**：连接的 `project` 是全平台默认项目；`subsystem.coding_project` 优先，为空时继承。
  两处都空时任务查询报 40000 并点名系统，空候选列表不会被误读成「这个项目没有任务」。
- **范围**：只做 `scope=GLOBAL`。表与领域已支持 `SUBSYSTEM` 覆盖，但引擎只解析 GLOBAL 一行，页面不暴露，
  避免「配了不生效」；每系统连接要改引擎的连接解析，放到 P3 一起做。
- **未做**：单元级绑定校验（任务存在 / 所属项目一致）仍排在后面；端点模板与状态词表仍在
  `coding-endpoints.yml`，改配置需要重启与评审。

1. 审批按**发布单**，不是按审批单 id（草案 `/approvals/{id}/approve`）：一个快照只有一条链，

#### 12.2.4 P4-A 已实现的接口：回滚与发布记录（真实路径）

回滚与全局发布记录的接口（`/api/v1` 前缀）；**以这张表为准**。

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/units/{id}/rollback-versions` | 回滚抽屉数据：当前线上版本 + 至多 10 个历史版本 + 必读提示 | 登录 + 单元数据范围（本接口不校验 `rollback:execute`，页面把按钮置灰） |
| POST | `/api/v1/rollbacks` | 单步执行回滚，body `{unitId, targetDigest, reason}` | `rollback:execute`（运维/管理员） |
| GET | `/api/v1/rollbacks?unitId=&page=&size=` | 回滚记录分页，最新在前；不带 `unitId` 时按调用者数据范围过滤 | 登录 + 数据范围 |
| GET | `/api/v1/rollbacks/{id}` | 单条回滚记录（实例号、结果、原因、来源/目标版本） | 登录 + 该单元数据范围 |
| GET | `/api/v1/releases?page=&size=&keyword=&status=&systemId=&unitId=` | 全局发布记录分页（GAP-10）：一行一个发布单，带最新实例 | 登录 + 数据范围 |

**分页参数（R44）**

- 新增的两个列表端点请求参数是 `page`（从 1 开始，缺省 1）/ `size`（1–100，缺省 10），响应字段是
  `{total, pageNo, pageSize, records}`；
- 旧列表（`/tasks`、`/units`、`/subsystems` 等）请求与响应都仍是 `pageNo` / `pageSize`；
- 前端只在 `web/src/api/index.ts` 的 `listReleases` 一处做这层映射，其余列表不动。

**`GET /api/v1/units/{id}/rollback-versions`**

- 响应 `data`：`{current, history[], warnings[]}`。`current` 与 `history` 元素同形：
  `digest`、`finishedAt`、`publishNo`、`executedBy`（历史行为空即 `null`，页面显示 `—`）、
  `batchCount`（整数，可能为 0）、`environments[]`（`{kind, label}`；`kind` 是机器值
  `PROD / DR / BLUE`，`label` 是中文名）。
- `history` 最多 10 条，当前镜像不在其中；`warnings` 是服务端固定三条必读提示（仅镜像、共库风险、
  立即执行不走审批），不是按版本生成。
- 错误码：40000 单元不存在；40001 该单元还没有成功的生产部署（页面据此显示空态，不当错误）；
  40009 单元不在数据范围。

**`POST /api/v1/rollbacks`**

- 请求 `{unitId, targetDigest, reason}`。`unitId` 为空或 ≤0、`targetDigest` 为空、`reason` 为空或
  超过 200 字都是 40000（`reason` 列 `VARCHAR(200)`）；空 body 同样 40000。
- 校验顺序（服务内）：`rollback:execute` → 单元存在与数据范围 → 原因 → 版本清单非空（40001）→
  目标在历史且 ≠ 当前（40000）→ 启用的 `PROD_DEPLOY` 绑定与生产族 DE（40011，载荷 `missing`
  指出缺哪项）→ 封板只生成提示 → 单元锁（40006，载荷带持有者 `instanceId/acquiredAt`）。
- 响应 `data`：`rollbackId`、`pipelineNo`、`unitId`、`targetDigest`、`freezeWarning`（无封板为
  `null`）。返回即已提交：记录与实例在同一事务落库，首节点在事务提交后推进。
- 错误码：40000 参数或目标非法；40001 没有可回滚版本，或当前线上版本的发布单不可用；40006 单元
  被占用；40009 无权限或越界；40011 缺生产配置。

**`GET /api/v1/rollbacks`**

- 参数：`unitId`（可选）、`page`（缺省 1）、`size`（缺省 10，1–100）。
- 响应 `data`：`{total, pageNo, pageSize, records[]}`；`records` 元素：
  `id / unitId / instanceId / pipelineNo / sourceOrderId / sourceItemId / sourcePublishNo /
  sourceDigest / sourceCommit / targetDigest / targetPublishNo / reason / requestedBy /
  status / statusLabel / failureReason / createdAt / finishedAt`。`status` 是
  `RUNNING / SUCCESS / FAILED`，`statusLabel` 是 `执行中 / 成功 / 失败`。
- 排序 `created_at DESC, id DESC`。无 `unitId` 且调用者没有任何单元范围时返回空页
  （fail-closed，不查库）。
- 错误码：40000 页码或每页条数非法；40009 `unitId` 越界。

**`GET /api/v1/rollbacks/{id}`**：单条记录，字段同上；40000 记录不存在；40009 记录所属单元越界。

**`GET /api/v1/releases`**

- 参数：`page`（缺省 1）、`size`（缺省 10，1–100）、`keyword`（发布单号或 CRID 包含匹配，≤64 字）、
  `status`（发布单状态精确匹配）、`systemId`、`unitId`。
- 响应 `data`：`{total, pageNo, pageSize, records[]}`；`records` 元素：
  `publishNo / itemId / crid / version / subsystemId / subsystemName / unitId / unitName /
  orderStatus / orderStatusLabel / itemStatus / itemStatusLabel / plannedReleaseTime / createdAt /
  executedBy / pipelineNo / pipelineStatus`。
- 一行一个发布单，`pipelineNo` / `pipelineStatus` 取该单 `MAX(id)` 的实例，从未执行为 `null`；
  `executedBy` 是 V25 列，历史单为 `null`。
- 数据范围 fail-closed：所有筛选与范围 AND，不会放大范围；显式 `unitId` 越界 40009，
  `systemId` 越界只得到空页（R45）；`status` 给未知值也是空页，不报错。
- 成本：一条 count + 一条 page；count 为 0 时不再查 page。
- 错误码：40000 页码、每页条数或关键字长度非法；40009 显式 `unitId` 越界。

**错误码含义（按代码）**

| 码 | 枚举 | 在这组接口里的触发点 |
|---|---|---|
| 40000 | `PARAM_INVALID` | 单元不存在、参数缺失或非法、目标不在历史或等于当前、原因空或超长、记录不存在、分页非法、关键字超长 |
| 40001 | `STATE_NOT_ALLOWED` | 单元没有成功的生产部署；当前线上版本的发布单/变更项不可用 |
| 40006 | `UNIT_LOCKED` | 单元被其他实例占用 |
| 40009 | `FORBIDDEN` | 没有 `rollback:execute`；单元或记录越出数据范围 |
| 40011 | `UNIT_NOT_CONFIGURED` | 缺启用的 `PROD_DEPLOY` 绑定或生产族 DE（`PROD / DR / BLUE`） |

**与草案的差异（已记录在台账）**

1. 请求用 `page/size`、响应用 `pageNo/pageSize`（R44）；草案 §12.1 的「`?page=1&size=20` 返回
   `{total,list}`」与旧列表的 `pageNo/pageSize` 都不是本组接口的形状。
2. `GET /releases` 多一个 `unitId` 筛选（草案只有 `systemId`）；`systemId` 在服务内叫
   `subsystemId`，落到 `deploy_unit.subsystem_id`，是同一列。
3. 没有「发起 → 待执行」两步（R39）：`POST /rollbacks` 同时创建记录与实例并开始执行。

## 14. 非功能实现

| 项 | 方案 |
|---|---|
| 可观测 | Micrometer + Prometheus；关键指标：`pipeline_active`、`node_duration_seconds`、`engine_error_total`、`gate_block_total`、`lock_expire_total` |
| 日志 | JSON 结构化，`traceId` 由网关注入并透传至引擎调用 |
| 审计 | `audit_log` 记录 before/after JSON，禁止物理删除 |
| 幂等 | 写接口 `Idempotency-Key`；webhook 事件去重表 |
| 对账 | 30s 扫描 `WAITING_EXTERNAL` 超 90s 未更新 |
| 补偿 | 实例长时间 `RUNNING` 且无活跃任务 → 标记 `STUCK` 并告警 |
| 容量 | 日 50 单、并发流水线 ≤ 50；单表年增约 10 万行，无分库需求 |
| 降级 | 引擎不可用 → 新建任务排队不发起，页面明确提示；已运行实例继续对账 |
| 安全 | 凭证加密、越权拦截、敏感字段脱敏、SQL 注入防护（MyBatis 参数化） |

**测试策略**
- 单元测试：状态机迁移矩阵全枚举（每个 (state,event) 组合断言合法/非法）；
- 集成测试：Testcontainers 起 MySQL/Redis，跑节点推进与锁竞争；
- 契约测试：MockWebServer 模拟 CODING 各类响应（成功/失败/超时/重复回调）；
- 并发测试：同一实例 10 线程并发回调，断言只推进一次。

## 15. 部署与发布

- 镜像：`release-api:{git-sha}`；配置经 ConfigMap，密钥经 Secret/KMS。
- 启动检查：Flyway 迁移 → 引擎连通性探测 → 就绪探针。
- 首次上线：初始化全局窗口（默认空=全程可用）、默认门禁规则、管理员账号。
- 灰度：先接入 1–2 个系统（低风险），观察 2 周豁免率与窗口外比例，再全量。
- 回滚平台自身：镜像回退；数据库变更全部向后兼容（只加列不改语义）。

## 16. 风险与未决

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | CODING 开放接口能力不明确（无法获取日志/产物/部署状态） | 核心链路可能受阻 | 落地第 1 周做接口 PoC，产出能力矩阵；缺失能力走降级方案 |

| R4 | 回滚仅镜像，代码与线上漂移 | 事故复盘困难 | 回滚页强制展示目标 commit 与「代码需人工回退」提示 |
