## 1. 背景与目标

### 1.1 背景与问题

一次上线要跨 Git、CODING、制品库、配置中心、测试/生产环境多套系统手工操作，问题集中在：

1. **发布单元割裂**：一个版本涉及多个部署单元与二方库，各自构建部署，缺少统一的「一次发布任务」视图，进度靠人问。
2. **门禁靠人记**：安全扫描、Sonar、组件漏洞是否通过靠人确认，无系统强制、无豁免留痕。
3. **状态不透明**：构建到哪一步、部署在哪个环境、卡在谁那里，没有统一时间线。
4. **合并靠人做**：功能分支何时合并回主分支、是否成功，无系统记录。
5. **平台强绑定**：构建部署逻辑写死在 Jenkins 任务里，换 CI 平台要重配。
6. **生产不受控**：窗口、封板、OA 工单、审批分散在人工流程，系统侧无卡点。

### 1.2 目标

1. **一次发布任务纳管多个变更项**，任务级看总进度，**执行按部署单元独立**，互不阻塞。
2. **发布动作标准化**：点「发布」即自动构建、部署测试环境；检查与部署并行，人工只在门禁处决策。
3. **门禁强制化**：安全检查「通过」或「豁免」+ 测试验收「通过」，两者同时满足才允许生产。
4. **生产发布受控**：OA 工单 + 发布窗口 + 重大事项封板 + 分级审批 + 运维执行，五道闸系统化。
5. **失败可重入**：按 commit 变化自动决定重跑范围，不重建任务、不重复劳动。
6. **发布即闭环（二期补全）**：一期以生产部署成功为完成；二期自动提 MR 合并功能分支，可追踪、可催办。
7. **CI/CD 可替换**：一期构建部署完全由 CODING 任务承载（任务预先配好）；二期把分支管理与构建打包部署收回自研，按语言标准化。

### 1.3 非目标（一期不做）

- 不做代码托管、不做 CI 引擎本身（复用 CODING）。
- 不做需求/工时/项目管理（只做关联）。
- 不做生产流量调度（灰度/蓝绿切流由网关或发布平台负责，本工具只做部署与回滚触发）。
- 不做配置中心本体（disconf/nacos/apollo 对接 → 二期）。
- 不做配置类变更下发、数据库变更/SQL 工单 → 二期。
- 不替代 OA/HR：只做 OA 工单号登记与格式校验，审批在本平台内完成。

### 1.4 反目标（技术成功但产品失败的样子）

- **门禁可被绕过**：豁免成了默认路径，人人点豁免，等于没有门禁。
- **状态靠人对账**：页面显示成功、实际没上去，或反之——信任崩塌后团队会绕开平台。
- **窗口设得过窄**：绝大多数发布落在窗口外，审批变日常，管控成本压垮收益。
- **比原来更慢**：点一次发布要多点五个页面，团队宁愿回滚到手工流程。
- **只覆盖一种语言**：Java 能用、Node 团队用不了，平台变成半个工具。
- **锁死发布**：一个卡住的流水线占住部署单元，后续发布全被挡住且无人能解。

### 1.5 成功度量（建议口径）

| 指标 | 目标方向 |
|---|---|
| 发布留痕率 | 100% |
| 豁免率 | 个位数百分比（过高说明门禁过严或误报多） |
| 窗口外发布占比 | ≤ 20% |
| 单次发布人工操作步数 | 相比现状下降 ≥ 50% |
| 失败平均定位时长 | 从「翻多个系统」降到「一页看日志」 |
| 发布成功率 / 回滚次数 | 按系统、部署单元统计 |

## 2. 名词与领域模型

### 2.1 核心实体

| 实体 | 说明 | 关键属性 |
|---|---|---|
| **系统** | 业务系统研发组织单元，如 `SCC-PORTAL-CORE-OS` | 名称、负责人、工具授权代理、研发协同资源、**管控配置** |
| **部署单元（模块）** | 可独立构建部署的最小服务单元，如 `quota-api` | 名称、ID、DU、owner、框架模板、分支模式、状态、代码库、镜像、环境配置、**3 个 CODING 任务关联（构建/测试部署/生产部署）** |
| **二方库** | 内部依赖包（jar/sdk），无部署动作，发布即产出制品 | 名称、owner、代码库、制品坐标、版本号 |
| **代码库** | Git 仓库；**一个代码库可被多个部署单元共用（共库）** | 仓库地址、基线分支（master）、CODING 项目 |
| **环境** | **日常环境**（开发自测，不跑检查）、**测试环境**（上线验证，跑检查）、**生产环境**（生产/容灾/蓝绿） | 环境标签、类型 |
| **DE** | 具体部署实例，如 `cwsp-quota-api-sit`、`cwsp-quota-api-dr` | 名称、环境标签、所属 DU、资源名、CODING 部署目标、**批次号** |
| **发布任务** | 一次上线需求的组织单位，如 `202609-V6.10.12` | 名称、系统、创建人、预计完成时间、目的、完成率、成员、关联需求 |
| **变更项（CRID）** | 最小发布单位 = 一个部署单元/二方库 + 一个 CODING 构建任务 | CRID、变更原因、单元、**分支（只读，来自 CODING 任务）**、计划发布时间、类型、**门禁状态**、测试人员、部署人员、基准 commit |
| **发布单** | 一个变更项的一次上线目标（原型「发布单号 624442」） | 发布单号、OA 工单、豁免、审批、发布记录 |
| **流水线实例** | 一次实际执行（原型「流水单号 4246887」） | 流水单号、执行类型（上线/日常）、触发方式、当前节点、状态 |
| **节点** | `构建` → `测试部署` → `验证确认` → `生产部署`（写基线 → 二期，C25） | 名称、起止、执行人、耗时、状态 |
| **节点任务** | 节点内原子任务（合并校验/包构建/镜像构建/部署/检查/合并MR） | 名称、状态、耗时、结果摘要、日志链接、**批次号** |
| **检查结果** | 单次扫描的产物 | 类型、执行阶段（镜像级/环境级）、状态、缺陷数、**最高等级**、报告链接、扫描对象 |
| **缺陷等级** | 严重/高危/中危/低危，决定处置（C12） | 等级、来源检查项、数量 |
| **豁免单** | 中危问题的放行凭证 | 发布单、覆盖检查项集合、commit 快照、申请人、审批人、有效期 |
| **发布窗口** | 允许生产发布的时间段；窗口内免审批 | 作用域、星期时段、例外日历、启用开关 |
| **封板事件** | 重大事项临时封版 | 发起人、范围、起止、事由、状态、解除人 |
| **发布审批单** | 生产发布人工审批记录 | 触发类型、会签人、结论、意见、时间 |
| **OA 工单** | 生产发布的外部凭证 | 工单号、提交人、提交时间、校验状态 |
| **MR 记录** | 合并请求（**二期**，写基线产物） | 仓库、源分支、目标分支、MR 链接、状态、关联变更项集合 |
| **占用锁** | 部署单元的上线发布互斥锁 | 单元、持有实例、获取时间、过期时间 |
| **CODING 任务关联** | 部署单元对应的 CODING 任务引用（C23/C24） | 构建任务、测试部署任务、生产部署任务、日常部署任务（可选） |

### 2.2 关系

```
系统 1 ── N 部署单元 / 二方库
部署单元 N ── M 代码库                    （共库：多单元共用一库）
部署单元 1 ── N DE（日常若干 + 测试 1 + 生产/容灾/蓝绿若干）
部署单元 1 ── 3 CODING 任务（构建 / 测试部署 / 生产部署）+ 可选 1 个日常部署

发布任务 1 ── N 变更项
变更项   1 ── 1 发布单（上线）             发布单号在重跑中保持不变
发布单   1 ── N 流水线实例（每次执行一个流水单号）
流水线实例 1 ── 4 节点（二期加写基线为 5 节点；日常类型仅 2 节点）
节点     1 ── N 节点任务（生产节点按批次拆分）
节点任务 1 ── N 检查结果（环境级检查挂 DE/批次）
检查结果 ── 汇总为发布单的缺陷等级
缺陷等级(中危) 1 ── 0..1 豁免单（覆盖检查项集合 + commit 快照）

发布单   1 ── 1 OA 工单（重跑复用，不重填）
发布单   1 ── 0..N 发布审批单（按提交批次生成，commit 变化则作废）
代码库+分支 1 ── 0..1 MR 记录（共库变更项共享同一 MR）
部署单元 1 ── 0..1 占用锁（上线发布互斥，随实例终态释放）
封板事件 / 发布窗口 ──> 参与准入判定（提交时快照 + 执行前复核）
```

### 2.3 关键约束

- **变更项独立执行**：同任务下多单元可并行处于不同节点，A 失败不影响 B。
- **共库风险**：多单元共库时「回滚镜像 + 代码」互相影响，回滚前强提示与影响面确认。
- **分支不由本平台管理**：一期分支来自 CODING 构建任务配置，平台只读展示，不创建、不编辑、不校验；**一期也不产生任何合并动作**（C21/C25）。
- **检查不阻塞测试**：测试部署成功即可开测；检查只卡生产准入。
- **构建一次，两处部署**：构建任务唯一，测试与生产**共用同一镜像/包**；生产部署前校验镜像 digest 与测试部署一致，不一致直接阻断（C23）。
- **生产即受控**：生产部署不放行「直接执行」，须过 OA → 窗口 → 封板 → 审批 → 运维执行，且**执行前复核**。
- **产物可追溯**：发布单必须能反查 commit、包、镜像、DE 与回滚入口。
- **锁必须可释放**：任何占用锁都有过期时间和管理员强拆入口，不允许「锁死」。

## 3. 角色与权限

| 角色 | 说明 | 关键权限 | 不能做 |
|---|---|---|---|
| 平台管理员 | 平台运维 | CODING 连接与**任务映射**、门禁规则、全局窗口/审批人、封板发起与解除、紧急放行、**强拆占用锁** | 无事前审批的强制生产（除非紧急放行留痕） |
| 系统负责人 | 原型「系统负责人」 | 系统下单元/二方库增删、owner 变更、系统管控配置、授权 | — |
| 工具授权代理 | 负责人代理人 | 代负责人审批/授权 | — |
| **部门经理** | 组织角色 | **封板发起**、封板期生产发布**会签** | — |
| **运维组长** | 组织角色 | 窗口外生产发布审批、封板期会签、**封板解除** | **发起代码版本变更** |
| **运维** | 执行角色 | **生产部署执行、回滚执行**；发起 SQL/配置变更（二期） | **发起代码版本变更** |
| 部署单元 owner | 原型 owner | 本单元流水线/环境配置、**发起代码发布**、发起回滚、（二期）合并 MR | 审批自己发起的生产发布 |
| 开发 | 分支开发者 | **在 CODING 侧**拉分支、提交部署任务、查看构建日志、发起日常发布、提交生产发布 | 生产执行 |
| 测试人员 | 变更项「测试人员」 | 查看部署与检查结果、点「测试通过/不通过」、**撤回**（仅本人） | — |
| 部署人员 | 变更项「部署人员」 | 生产发布协同（查看、催办、备注） | 执行生产部署 |
| **产品** | 发布任务成员「产品」角色 | 查看进度与发布计划、**接收封板与发布通知** | — |
| 安全/质量审核人 | — | 豁免审批、查看扫描结果 | — |

**角色边界（C20）**
- **代码版本变更（分支变更）的发起人只能是开发/部署单元 owner**；运维与运维组长无此权限。
- **运维/运维组长只能发起 SQL 变更与配置变更**（二期模块），用于运维侧改动。
- **SQL/配置变更不存在自审批**：发起人若已具备该类变更的审批权，**免审批直接执行**，但必须留痕。
- **代码发布禁止自审批**：发起人不得审批自己提交的生产发布，系统自动转给代理或上级。

权限落到**按钮级**（发布、日常、测试通过、撤回、生产执行、审批、豁免、回滚、封板、强拆锁、配置修改），按「角色 × 数据范围（系统/部署单元）」控制。

## 4. 端到端业务流程

### 4.1 主流程

| 步 | 动作 | 执行方 | 系统行为 |
|---|---|---|---|
| 1 | **拉分支开发** | 开发 | 按团队既有方式在 CODING 侧拉分支；**本平台不参与分支创建与管理**（C21） |
| 2 | **提交部署任务** | 开发/owner | 任务下加「分支变更」：单元/二方库 + 变更原因 + 计划发布时间；**分支自动只读带出**自 CODING 任务；一次任务可加多条 |
| 3 | **点击发布** | owner/开发 | 按变更项独立触发：生成发布单 → 流水线实例 → 进入「构建」 |
| 4 | **自动构建打包** | 系统→CODING | 合并校验 → 编译打包 → 构建镜像 → 产物入库；**镜像级检查同时启动** |
| 5 | **部署测试环境** | 系统→CODING | 部署到测试 DE；**成功即可开测**，并触发**环境级检查** |
| 6 | **门禁收敛** | 系统+人 | 检查按等级判定；测试人员点「测试通过」；两者独立、互不阻塞 |
| 7 | **提交生产发布** | 开发 | 选**计划生产发布日期时间** + 填 **OA 工单号** → 系统判定窗口/封板 → 生成审批单（如需）（C22） |
| 8 | **生产执行** | 运维 | 复核准入 → 点「执行发布」→ 分批串行部署 |
| 9 | **发布完成** | 系统 | 生产部署成功即「已完成」；**写基线与合并功能分支 → 二期**（C25） |

### 4.2 流程图

```
拉分支开发（CODING 侧完成，平台不参与）
   ↓
[发布任务] 部署变更 ×N（部署单元 / 二方库）
   ↓ 按变更项独立
点击发布 → 发布单 → 流水线实例
   ↓
① 构建：合并校验 / 包构建 / 镜像构建 ──→ 镜像级检查（Sonar/组件/架构/版本缺陷）
   ↓ 产物与镜像唯一，测试与生产共用（C23）
② 测试部署：调用测试部署任务 → 测试环境 DE ──→ 环境级检查（安全动态测试/自动化测试/SQL规范）
   ↓ 完成即可开测
③ 验证确认（门禁汇总）· 结果后台累积，不阻塞测试
   ↓ 测试通过 ＋ 检查通过或豁免（两条件正交）
④ 提交生产发布（选计划时间 + 填 OA 工单）→ 窗口/封板判定 → 审批（如需）
   ↓ 运维复核 → 生产部署（调用生产部署任务，校验同一镜像）→ 分批串行：主生产→主容灾→蓝绿生产→蓝绿容灾
⑤ 发布完成：生产部署全部成功 → 已完成
   （无合并动作；写基线 + 自动提 MR 随分支管理移入二期，C25）
```

### 4.3 门禁并行时序

```
时间轴 →→→
构建       ████████
镜像级检查     ██████████              （构建成功即触发）
测试部署              ████████
环境级检查                ██████████     （部署成功才触发）
开测                        ▓▓▓▓▓▓▓▓▓▓  （随时可点通过）
门禁判定                                ● 两条件同时满足 → 可提交生产
提交生产发布                              ██ OA+窗口+封板+审批
生产部署                                    ████████
```

**规则**
- **镜像级检查**：Sonar、应用组件漏洞、架构规范、版本缺陷 —— 依赖镜像/产物，构建成功即跑。
- **环境级检查**：安全动态测试、自动化测试、数据库规范 —— 依赖已部署环境，测试部署成功才跑。
- 测试部署失败/重试时，**已完成的镜像级检查结果保留并继续有效**（绑定镜像 digest）；环境级检查作废重跑。
- 检查项可单独刷新，晚到结果实时更新门禁状态。
- 「测试通过」与「检查通过」无先后要求；任一方反向会**收回**生产准入（处理见 4.6）。
- 不满足时按钮置灰并列出**具体缺项**与**能否豁免**。

**P2 落地说明（实现口径，不改变上面规则）**

- 七项检查在**验证确认节点进入时**统一触发（此时测试部署已成功）。镜像级检查本可在构建成功后
  提前并行触发，属性能优化，不影响判定（判定只在测试部署之后才有意义）。
- 检查结果是外部异步回传：30s 轮询，单项 30 分钟未出结果判超时（`TIMEOUT`，记未通过）。
- 引擎不可达/返回无法判定的状态记为「未完成」并重试，**绝不读作通过**。
- 判定用「本次所有检查项的最高等级」：`严重/高危` 阻断且不可豁免；`中危` 阻断但可豁免；
  `低危` 仅告警；无问题通过。
- 中危阻断**不结束变更项**：停在「测试中」等豁免决定，避免「一有中危就得整体重跑」。
  高危阻断、结果失效、测试不通过/撤回则直接进「门禁未通过」。

### 4.4 状态机

**主状态**（`release_item.status`）

| 状态 | 进入条件 | 可转到 |
|---|---|---|
| 待发布 | 变更项创建完成 | 发布中（构建）、已关闭 |
| 发布中（构建） | 点击发布 | 测试中、失败 |
| 测试中 | 构建 + 测试部署成功 | 待生产准入、门禁未通过、失败 |
| **门禁未通过** | 测试不通过 或 检查不通过（未豁免） | 测试中（重新发布）、已关闭 |
| 待生产准入 | 两门禁均满足 | 待提交、门禁未通过 |
| **待提交** | 两门禁满足、尚未提交生产 | 待审批、待执行、门禁未通过 |
| 待审批 | 提交后窗口外或封板期 | 待执行、已驳回、门禁未通过 |
| 待执行 | 审批通过 或 窗口内免审批 | 发布中（生产）、待审批（封板在途转入）、门禁未通过 |
| 发布中（生产） | 运维执行 | 已完成、失败 |
| **已完成** | **生产部署全部成功**（一期无 MR 合并环节，C25） | 已回滚 |
| 已驳回 | 审批不通过 | 待提交（重新提交）、已关闭 |
| **失败** | 节点失败（构建/测试部署/生产部署） | 测试中（重跑）、已关闭 |
| 已关闭 | 人工关闭变更项 | — |
| 已终止 | 退出流水线（实例级） | 测试中（重新发起） |

**门禁维度之一：检查**（`release_item.gate_status`，与主状态正交）

| 值 | 含义 |
|---|---|
| `CHECK_RUNNING` | 检查执行中（含「还没开始」与「引擎没回话」，都读作未完成） |
| `CHECK_PASS` | 检查通过（最高等级 ≤ 低危） |
| `CHECK_WAIVED` | 中危且已豁免（附豁免单） |
| `CHECK_FAIL` | 检查不通过（含高危，不可豁免） |
| `CHECK_INVALID` | 检查结果失效（commit/镜像变化、部署重试、豁免到期） |

**门禁维度之二：测试**（`release_item.test_status`，同样正交）

| 值 | 含义 |
|---|---|
| `TEST_PENDING` | 未测试 / 测试中 |
| `TEST_PASS` | 已通过（记录通过人、时间） |
| `TEST_FAIL` | 测试不通过（附原因） |
| `TEST_REVOKED` | 已撤回（仅本人可操作） |

> **为什么拆成两列（P2 修正）**：v1.5 之前把上面两组值塞在同一个 `gate_status` 里，一个维度
> 写入就会覆盖另一个（记录检查结果会抹掉「测试不通过」）。两个门是正交的，一列装不下：
> 现在各占一列，页面分列展示。

**说明**：主状态是「走到哪一步」，门禁维度是「两道门各自什么结果」。UI 上分别渲染，避免用单一状态硬塞正交关系。

**节点状态**：未开始 / 等待中 / 进行中 / 成功 / 失败 / 阻塞（待人工）/ 已跳过 / **部分成功（批次级）**
**审批状态**：无需审批 / 待审批 / 会签中 / 通过 / 驳回 / 已撤销

### 4.5 重新发布规则（C15）

```
点击「重新发布」
   ↓
比对 该变更项对应代码路径的 HEAD commit 与基准 commit
   ├─ 相同 → 从「失败节点」重跑
   │         · 新建流水线实例（发布单不变，流水单号变）
   │         · 复用已构建镜像与产物
   │         · 镜像级检查结果有效（绑定镜像 digest），不重跑
   │         · 环境级检查按需重跑
   │         · 已通过的「测试通过」保留（产物未变）
   │         · 生产审批需重新判定（窗口/封板可能已变）
   │         · 生产重跑为批次级，已成功批次不重部署
   └─ 不同 → 从「构建」全量重来
             · 重新构建、重新出镜像
             · 全部检查重跑，门禁结果重置
             · **「测试通过」自动作废**（需二次确认 + 留痕，C19）
             · 已有审批单作废，OA 工单保留可复用
```

**共库特殊处理**：多单元共库时，commit 比对按**该单元对应的代码路径**（如 `outbound-os/` 子目录）过滤，避免他人提交误判为本单元变更。路径未配置时降级为整库 commit 比对并在页面提示风险。

页面明示重跑范围与原因（「代码有更新，需全量重来」/「代码未变，从生产部署重跑」）。

### 4.6 准入快照与失效（C16）

**快照**：点「提交生产发布」时，系统生成准入快照（检查最高等级、测试结论、OA 工单号、窗口内/外、是否封板、应走的审批链），并据此生成审批单。

**复核**：运维点「执行发布」前，系统**再次校验**：
- 封板状态是否变化（提交后新封板 → 转双签）；
- 检查/测试是否被撤回或失效；
- 豁免是否过期。

**失效处理（C16）**

| 失效发生在 | 处理 |
|---|---|
| 待提交 / 待审批 | 回到「门禁未通过」或「待提交」，审批单作废，通知相关人 |
| 待执行（尚未执行） | 撤销执行资格，回到「待审批」，需重新审批 |
| 生产已开始（部分批次已上线） | **已上线批次不回滚**；**后续批次暂停**；运维可「继续执行」或「停止发布」；停止即转「失败」，已上线部分保留并提示回滚入口 |
| 豁免到期 | 视为 `CHECK_INVALID`；若生产已开始，同上处理 |

**原则**：门禁只对「还没发生的事」有否决权，对「已经发生的事」只有提示权。绝不由系统自动回滚已上线批次。

### 4.7 并发与占用锁

- **锁粒度**：部署单元（不是代码库、不是系统）。
- **互斥范围**：同一部署单元的**上线发布**互斥；日常发布**不占上线锁**（允许多次并行），但共用 CODING 构建并发槽。
- **跨任务**：锁是全局的，两个任务对同一单元发起上线发布，后到者被拒绝并提示持有者。
- **回滚**：回滚占用同一把锁（回滚期间禁止并发上线发布）。
- **释放**：实例进入终态（已完成/失败、已关闭、已终止）即释放；异常残留按**过期时间**（默认 4 小时，可配）自动释放。
- **强拆**：管理员可强制释放，需填理由并留痕，通知锁持有者。
- **共库**：共享代码库的多个单元**各自持有独立锁**，但构建并发受限；页面提示「本库另有 N 个单元正在发布」。

### 4.8 终止与归档语义

| 动作 | 作用对象 | 结果 | 级联 |
|---|---|---|---|
| **退出流水线** | 流水线实例 | 实例 → 已终止；变更项 → 可重新发布 | 取消 CODING 侧构建/部署任务；**释放占用锁**；未跑完的检查标记失效 |
| **关闭变更项** | 变更项 | → 已关闭；不可再发布 | 释放占用锁；作废未完成的审批单（一期无 MR 环节） |
| **退出任务** | 发布任务 | 任务 → 已归档只读 | 级联关闭所有未完成变更项；释放全部锁；取消在途实例；**保留发布记录与回滚入口** |

**归档后的回滚**：由 owner 或运维发起（owner 只读不构成障碍，回滚属于运维动作），权限按 5.7 判定。

### 4.9 异常分支

| 场景 | 表现 | 处理 |
|---|---|---|
| 构建失败 | 节点红 | 看日志 → 节点重试 或 重新发布 |
| 测试部署失败/超时 | 环境卡红（超时可配，原型 8 分钟） | 「重新部署」；镜像级检查结果保留 |
| 检查不通过 | 门禁红，生产按钮锁定 | 按等级：高危修复重跑；中危可申请豁免 |
| 测试不通过 | 测试人员点「不通过」 | 原任务重新发布（C11） |
| 检查晚到且失败 | 准入被收回 | 按 4.6 处理（已上线不回滚） |
| 窗口外提交 | 进「待审批」，通知运维组长 | 通过后转「待执行」 |
| 封板期提交 | 双签 | 会签通过才可执行；在途发布自动转入 |
| 封板在途生效 | 待提交/审核中/待执行 → 待审批（双签） | 需补双签；**企微机器人通知产品/研发/测试/运维**；解除后已签意见保留，缺的补齐 |
| 审批超时 | 超 12h 未处理 | 提醒；超 24h 升级上一级 |
| 生产分批失败 | 第 N 批失败 | **立即停止后续批次**；已成功批次保留；运维可重试该批或停止并回滚 |
| 合并与代码回退 | **二期** | 一期不产生合并动作；合并冲突处理与 MR 跟踪随「写基线」一并二期交付（C25） |
| 锁被占用 | 发起发布被拒 | 显示持有者与开始时间；可催办或管理员强拆 |

## 5. 功能需求

### 5.1 基础资源管理

**FR-R-01 系统列表与详情【一期】**
- 列表：名称、负责人、部署单元数、二方库数、部署状态、**管控状态（当前窗口/是否封板）**；搜索。
- 详情 4 Tab（对齐原型）：
  1. **研发协同资源**：Git 仓库、CODING 项目、制品库、Jenkins（兼容保留）、SVN 产品库、Confluence 空间；每项可「授权」。
  2. **部署单元（模块）**：运行中/已下线两 Tab；「创建新部署单元」「创建二方库」；统计「共 N 个部署单元，M 个二方库」。
  3. **数据库配置信息**：【二期】。
  4. **部署状态**：各 DE 当前运行版本。
- **管控配置**入口：发布窗口、封板适用范围、审批人（运维组长/部门经理）。

**FR-R-02 部署单元管理【一期】**
- 创建类型：部署单元 / 二方库。
- 基本信息：名称、DU、owner、框架模板、分支模式（标准/兼容）、状态、描述；**创建后可在详情页编辑并保存**（整体替换，subsystem 归属不可改）。
- 筛选标签：**模块**（module，自由文本）与**标签**（tag，单值）—— 只用于列表筛选与展示，**不进入构建/部署参数**，与下面的「模块路径」不是同一件事。
- 代码信息：代码库名、地址、**模块路径**（共库时用于 commit 比对与产物定位）；创建时校验占用并提示影响面。
- 部署信息：部署类型、镜像类型、镜像名称（**测试与生产共用同一镜像**，C23）。
- **CODING 任务关联（C23/C24）**：
  - **构建任务**（唯一，必填）—— 出包与镜像；
  - **测试部署任务**（必填）—— 部署到测试环境 DE；
  - **生产部署任务**（必填）—— 部署到生产/容灾/蓝绿 DE，**复用构建任务的镜像**；
  - **日常部署任务**（可选；不填则复用测试部署任务，仅切换目标环境）。
  - **任务从 CODING 查询选择**：按所属系统的 CODING 项目拉取该项目的构建任务 / 部署任务清单供选择，而不是手工填 ID；查询不可用（连接未配置）时可退回手工填写。
  - 每项提供「连接测试」：任务存在、所属项目一致、当前凭证可触发；三项必填未配齐时不允许发起上线发布。
- **环境配置（C10）**：
  - **测试环境**：1 个 DE，跑环境级检查。
  - **日常环境 1..N**：若干 DE，不跑检查。
  - **生产环境**：生产 & 容灾（及蓝绿）多 DE，**每 DE 配批次号**（C14）。
  - 「刷新资源」从 CODING/容器平台同步 DE。
- Tab：概述 / 变更明细 / 流水线配置 / 操作日志 / 发布记录 / disconf（二期）/ 应用配置（二期）/ 部署配置（二期）/ 消息通知。

**FR-R-03 二方库管理【一期】**
- 与部署单元同构，**无部署与环境配置**；维护制品坐标（groupId/artifactId）、版本规则、依赖它的部署单元列表（影响面）。

**FR-R-04 部署单元列表【一期】**
- 全局：ID、名称、系统、类型、owner、状态、最近发布版本、最近发布时间、**当前占用锁状态**；批量下线/转移 owner。
- 筛选：系统、类型、**模块**、**标签**（后两者精确匹配）、名称关键字。

### 5.2 分支与变更登记

**FR-B-01 变更登记【一期仅分支变更】**
- 任务下 Tab：**分支变更**、数据库变更（二期）、disconf 变更（二期）、应用配置变更（二期）、部署配置变更（二期）。
- 分支变更字段：单元/二方库（可多选批量添加）、变更原因、计划发布时间。**分支不在本页录入**，由单元绑定的 CODING 构建任务只读带出（C21）。
- 校验：同任务同单元不可重复；单元必须已配齐**构建任务 + 测试部署任务 + 生产部署任务**，且构建任务的分支可读取。
- **发起人限制（C20）**：分支变更仅开发/owner 可创建；运维与运维组长不显示该入口。
- 二方库无「日常」入口。

**FR-B-02 创建分支变更 & 批量部署【一期】**
- 「创建分支变更」按钮；勾选多行 →「批量部署」（按变更项独立创建流水线，逐个校验占用锁）。

**FR-B-03 分支只读展示【一期，C21】**
- 一期**不做分支管理**：不创建、不重命名、不做命名规则校验、不处理保护分支。
- 分支由单元绑定的 CODING 构建任务**只读带出**，展示于任务列表与发布内容页供追溯，不可编辑。
- CODING 任务为「多分支参数化」模式（分支需运行时传入）的，**一期不纳入可选范围**，列入二期。

### 5.3 发布任务

**FR-T-01 任务列表与卡片【一期】**
- 卡片：任务名、创建人（工号）、创建时间、关联系统、预计完成时间、目的、**完成率**。
- 筛选：系统、状态、时间；「我参与的」「我负责的」。

**FR-T-02 任务详情【一期】**
- 列：序号（拖拽）、ID（CRID）、变更原因、部署单元、分支（复制）、计划发布时间、类型、状态、**门禁状态**、操作（**发布**、**日常**、**关闭**）。
- 行内：发布 → 发布内容页；日常 → 日常发布；关闭 → 终止该变更项。

**FR-T-03 成员与工作项【一期】**
- 成员信息：成员、角色（测试/部署/开发/负责人）。
- 关联工作项：「+ 关联需求」，展示关联任务号与需求数。

**FR-T-04 完成率【一期】**
- 完成率 = 已完成变更项 / 总变更项（J9）。
- **一期以生产部署成功即计入完成**；二期再引入「已发布未合并」的未闭环标记。
- 二方库入库成功即完成。
- 任务级聚合状态：全部完成 / 部分进行中 / 有失败 / 有阻塞（待测试/待审批/待执行）。

**FR-T-05 退出任务 / 归档【一期】**
- 二次确认；级联见 4.8；归档后只读，保留发布记录与回滚入口。

### 5.4 发布流水线（核心）

**FR-P-01 发布内容页【一期】**

```
┌ 返回 │ 发布内容 | 发布记录                       [进入生产回滚] ┐
├───────────────────────────────────────────────────────────┤
│ ● 构建    ● 测试部署    ◐ 验证确认    ○ 生产部署           │
│ 2分18秒     成功(可开测)  5/7 通过     未开始        未开始   │
├───────────────────────────────────────────────────────────┤
│ 发布单 624442 │ 流水单 4246887 │ 节点 验证确认 │ 门禁:检查中/未测│
├───────────────────────────────────────────────────────────┤
│ CRID │ 变更原因 │ 分支 │ 类型 │ 计划时间 │ 测试人员 │ 部署人员  │
├───────────────────────────────────────────────────────────┤
│ 节点任务列表（状态 / 耗时 / 结果摘要 / 操作）                  │
│ [退出流水线] [刷新]                                          │
└───────────────────────────────────────────────────────────┘
```
- 步骤条：4 节点（写基线为二期），完成绿勾、进行中橙钟、未开始空心；节点下显示耗时。
- 节点信息条：发布单号、流水单号、节点、执行人、时间、耗时、状态、**门禁双维度角标**。
- 节点任务列表：名称、状态、耗时、结果摘要/徽标、操作（查看结果/刷新/日志/重试/重新部署/详情）。
- 「进入生产回滚」常驻。

**FR-P-02 ① 构建节点【一期】**
- **合并校验**：结果、基线分支、冲突提示、详情。
- **包构建**：耗时、包信息可下载、「更多」展开、「包构建日志」。
- **镜像构建**：耗时、镜像名、「镜像构建日志」、「重试」。
- 调该单元的**构建任务**（唯一）触发构建，异步回传（webhook 优先、轮询兜底）；产物与镜像**同时供测试与生产使用**（C23）。
- **产物、镜像 digest、commit 入库**，供重跑判定、镜像一致性与回滚使用。
- **构建成功即触发镜像级检查**，不等部署。

**FR-P-03 ② 测试部署节点【一期】**
- 每个测试环境/DE 一张卡片：环境名、状态徽标、节点名、耗时、镜像名、操作「查看详情」「重新部署」。
- 多环境并行；单环境失败不阻断其它；**超时可配**（原型 8 分钟）。
- 调用该单元的**测试部署任务**，目标为测试环境 DE。
- **部署成功立即**：通知测试人员、解锁「测试通过」、**触发环境级检查**。
- 重新部署时：环境级检查作废重跑，镜像级检查结果保留。

**FR-P-04 ③ 验证确认节点（门禁汇总区）【一期】**
- **非串行阻塞阶段**，而是结果汇总：
  - 检查项按阶段分组展示：**镜像级**（Sonar/组件/架构/版本缺陷）、**环境级**（安全动态测试/自动化测试/数据库规范）。
  - 每项：状态、耗时、结果徽标、操作「刷新结果」「查看结果」。
- **门禁账**：显示「已通过 5 / 7」、**最高缺陷等级**、处置结论（阻断/可豁免/仅告警）。
- **测试通过**：测试人员按钮，填结论；不通过填原因；**任一人通过即通过（C18）**，显示通过人与时间。
- **撤回**：仅**该测试人员本人**可撤回（C19），需填理由；owner/管理员不可代撤。
- **准入结论**：两条件满足 → 「可提交生产发布」，展示计算过程。

**FR-P-05 ④ 生产部署节点（受控）【一期】**
- 生产 & 容灾多 DE 部署；**分批串行、失败即停**（C14），批次顺序由 `env_de.deploy_batch_no` 决定（默认按环境类型）。
- 调用该单元的**生产部署任务**；**部署前强校验镜像 digest 与测试部署所用一致**（同一镜像），不一致则阻断且不可豁免（C23/J27）。
- **批次级状态**：每批显示批次名、DE 列表、状态、耗时；当前批次可重试。
- 已成功批次在重跑时**不重复部署**（J）。
- 门禁失效时按 4.6：暂停后续批次，运维可继续或停止。
- 审批通过后由**运维**点「执行发布」；执行前二次复核。

**FR-P-06 ⑤ 写基线节点【二期，C25】**
- 一期不交付本节点：发布完成 = 生产部署成功，平台不创建 MR，合并由团队在 CODING 侧自行处理。
- 二期（与分支管理一起）：自动提 MR（功能分支 → master 或配置基线），回填 MR 链接、目标分支、commit；同一 `(仓库, 分支)` 只创建一张 MR，共库多变更项共享。
- 二期节点状态：`MR 已创建` → `等待 owner 合并` → `已合并`；MR 失败/未合并不影响已完成的发布状态，只标「未闭环」。

**FR-P-07 流水线控制与重跑【一期】**
- 退出流水线、刷新、节点/任务重试、重新部署（级联见 4.8）。
- **重新发布（C15/4.5）**：按 commit 变化自动判定，页面明示范围与影响。
- **重跑生产节点为批次级**：只重跑失败批次及之后，不重跑已成功批次。
- 并发控制见 4.7；发起前校验占用锁，占用则拒绝并提示持有者。

**FR-P-08 发布记录【一期】**
- 发布内容页「发布记录」Tab：本次流水线全部节点执行历史（含每次重跑）。
- 全局「发布记录及回滚」：按系统/单元/时间检索。

**FR-P-09 二方库发布流水线【一期，独立编排】**

| 节点 | 内容 | 检查 |
|---|---|---|
| ① 构建 | jar 打包、坐标与版本号生成 | — |
| ② 安全检测 | 安全测试 / Sonar / 组件漏洞（**只跑与制品相关的三项**） | 按 C12 分级 |
| ③ 入库 | 通过或豁免后上传正式制品库 | — |

- **先检测、通过后入库**（C13）：不通过则终止，不入正式仓库，下游物理上拉不到。
- **无测试部署、无生产部署、无写基线、不需要「测试通过」**（不复用通用四节点，避免空节点）。
- 入库成功即变更项「已完成」，计入完成率。
- 中危豁免后入库的版本，豁免到期不自动下架，但版本详情标「豁免入库（到期时间）」，下游引用时提示。

### 5.5 质量门禁与安全

**FR-Q-01 检查项与触发阶段【一期】**

| 检查项 | 触发阶段 | 依赖 |
|---|---|---|
| Sonar 扫描 | 镜像级 | 构建产物/commit |
| 应用组件漏洞 | 镜像级 | 镜像/依赖清单 |
| 架构规范 | 镜像级 | 代码/产物 |
| 版本缺陷 | 镜像级 | 版本与已知缺陷库 |
| 安全动态测试 | 环境级 | 已部署环境 |
| 自动化测试 | 环境级 | 已部署环境 |
| 数据库规范 | 环境级 | 已部署环境/DB |

- 结果存证：报告链接、问题数、最高等级、扫描时间、扫描对象（commit/镜像 digest/DE）。

**FR-Q-02 缺陷等级与处置【一期，C12】**

| 最高缺陷等级 | 处置 | 谁能放行 | 留痕 |
|---|---|---|---|
| 严重 / 高危 | **阻断，不可豁免** | 无人（只能修复重跑） | — |
| 中危 | **阻断，可豁免** | 安全审核人审批 | 永久 |
| 低危 | **仅告警**，不阻断 | — | 记录 |
| 无问题 | 通过 | — | — |

- 判定口径：取本次发布单**所有检查项的最高等级**（而非逐项独立判定）。
- 检查项启停与等级阈值可配。

**FR-Q-03 豁免机制【一期】**
- **签发粒度**：一张豁免单覆盖「发布单 + 检查项集合 + commit/镜像快照」，中危项一次签完，不按检查项逐张签。
- 申请：中危阻断项可申请（原因、影响评估、有效期）。**有效期必填且最长 90 天**；同一变更项同时只有一张生效或待审的豁免单。
- 审批：安全审核人（运维组长/管理员，权限点 `gate:waive`，可配）；**不能自审**——申请人与审批人必须是两个人，管理员也不例外。
- **失效**：commit/镜像变化 → 自动失效；到期 → 失效（`CHECK_INVALID`）；失效处理见 4.6。
- 新增高危 → 豁免不覆盖，直接阻断（申请接口直接拒绝）。
- 与测试门禁解耦：豁免只解检查门禁。
- 待审豁免**不计入**门禁；被驳回即维持阻断。

**FR-Q-04 测试验收【一期】**
- 「测试人员」取自**发布任务的成员角色 TEST**（不是平台角色）；多人员时**任一人通过即通过（C18）**，责任落到点击人。
- 通过的前提：测试环境已就绪（测试部署成功），否则按钮置灰并说明原因。
- 不通过：需填原因，原因对所有人可见（记入 `test_fail_reason`）。
- 撤回：仅**本人**（C19），需填理由并记录；已通过时只能先撤回、再改判不通过。
- commit 变化导致的全量重跑，**自动作废**已有「测试通过」，需**二次确认 + 留痕**。
- 平台管理员可代为操作（break-glass），仍留痕。

### 5.6 生产发布管控（窗口 / 封板 / OA / 审批）

**FR-G-01 发布窗口管理【一期】**
- 层级：**全局默认 → 系统覆盖**（C7）。
- 定义：星期 + 时段（如「工作日 22:00–24:00」「周末全天」）、例外日历（节假日单独开关）、启用开关。
- 判定：以**开发提交时选定的计划生产时间**为准（C22/J5），不是提交瞬间；跨零点窗口需支持；**执行前复核封板但不重算窗口**。
- 展示：「当前是否在窗口内」+「下一个窗口」；窗口过长/过短的配置告警。

**FR-G-02 重大事项封板【一期】**
- 发起：**平台管理员或部门经理**；字段：范围（全局/指定系统）、起止时间、事由、影响说明。
- 生效：范围内所有**生产部署**转入双签（拦而不拒，C8）；构建、测试环境、日常发布不受影响。
- **在途处理**：封板发起时处于「待生产准入」「待提交」「待执行」或「发布中（生产）」的发布单——前三者转入双签；**生产中**的按 4.6 处理（不打断已上线批次）。
- 解除：**运维组长 / 发起人 / 管理员**；记录解除人、时间、原因；解除后重新计算准入，已完成的会签意见保留，缺的补齐。
- **生效通知（C22）**：封板生效时通过**企微机器人**强通知受影响发布单相关的**产品、研发、测试、运维**（任务成员按角色 + 系统负责人兜底），内容含封板范围、起止时间、事由、受影响发布单列表及其当前环节（待提交/审核中/待执行）。
- 页面：封板管理页（列表、顶部横幅、倒计时）；受影响发布单显著标识。

**FR-G-03 OA 工单登记【一期】**
- **在「提交生产发布」时由提交人（开发）填写**，必填；格式校验（J6）。
- 绑定**发布单**层级：重跑复用同一工单，不重填；多批次 DE 共用一张工单。
- 展示：工单号、提交人、提交时间；发布记录可检索。
- 预留 OA 对接接口（校验存在性/状态），一期不实现。

**FR-G-04 分级审批【一期】**
- 判定：窗口内且未封板 → **免审批**；窗口外 → **运维组长**单签；封板期（含窗口内）→ **运维组长 + 部门经理**双签。
- 会签顺序：先运维组长、后部门经理（J7）。
- **禁止自审批**（C20）：发起人不得审批自己提交的代码发布；命中时系统自动转给代理/上级。
- 操作：通过 / 驳回 / 撤销 / 转交；驳回需填意见。
- 时效：12h 未处理提醒，24h 升级（可配）。
- **审批单绑定提交批次**：commit 变化则作废重走；commit 未变的重跑，审批需重新判定（窗口/封板可能已变）。

**FR-G-05 准入判定引擎【一期】**

```
「提交生产发布」（开发，选定计划日期时间 + 填 OA 工单）
  ├─ ① 检查门禁：最高等级 ≤ 低危 或 中危已豁免？ ──否──> 阻断（列缺项）
  ├─ ② 测试门禁：测试通过？                      ──否──> 阻断
  ├─ ③ OA 工单：已填且格式合法？                 ──否──> 阻断
  ├─ ④ 窗口判定：在窗口内？ ──是──> 免审批 ────────┐
  ├─ ⑤ 封板判定：封板期内？ ──是──> 双签 ─────────┤
  │     └─ 窗口外且非封板期 ──> 运维组长审批 ──────┤
  └─ ⑥ 生成准入快照 → 待执行                      │
                                                  ↓
「执行发布」（运维）
  └─ 复核快照：封板变化？门禁失效？豁免过期？
        ├─ 无变化 ──> 执行（分批串行）
        └─ 有变化 ──> 退回按 4.6 处理
```
- 每次判定输出**明确原因 + 下一步动作**，不允许「按钮灰着但不给理由」。
- 判定结论可追溯（谁判定、何时、依据哪条规则）。

**FR-G-06 提交生产发布【一期，C22】**
- 入口：发布内容页「提交生产发布」；权限：**开发**（部署单元 owner 亦可；运维不可发起，C20）。
- 必填两项：**计划生产发布日期时间**（日期 + 时间点，精确到分钟）、**OA 工单号**。
- 系统按系统窗口规则判定该时间：落在窗口内 → 免审批，直接「待执行」；窗口外 → 生成运维组长审批单。
- 页面同时展示：该时间所属窗口、**下一个可用窗口**（便于改期）、当前封板状态。
- 提交后进入「待执行」，登记**计划执行时间与逾期阈值**；通知审批人（如需）、运维组与任务成员。
- **提交 ≠ 执行**：提交只登记意图与时间，实际执行由运维在时间点操作（FR-G-07）。

**FR-G-07 生产执行【一期】**
- 仅**运维**可点「执行发布」；记录执行人、时间、DE 列表、批次结果。
- 调 CODING 部署；失败可单 DE/单批次重试；失败即停后续批次（C14）。
- 门禁失效时（C16）：暂停后续批次，提供「继续」与「停止发布」两个动作，均需填理由。
- 紧急放行（仅管理员，可配）：需填理由并**红色高亮留痕**（J11）。

**P3 实现范围（2026-11-23）**

- **已实现**：FR-G-01 窗口（全局默认 + 系统覆盖、星期规则、例外日历、跨零点、执行前不重算窗口、
  「下一个窗口」）；FR-G-02 封板（声明即治理、在途转双签、解除/到期重算、列表与横幅）；
  FR-G-03 OA 工单（必填 + 格式校验，随发布单复用）；FR-G-04 审批（免审/单签/双签、顺序会签、
  禁止自审、通过/驳回；审批链按快照保存，重新提交不覆盖历史）；FR-G-05 六步判定（每条给原因 +
  下一步动作，试算不落库）；FR-G-06 提交（计划时间 + OA 工单）；FR-G-07 生产执行（分批串行、
  失败即停后续批次、批次边界暂停/继续、执行前复核、生产重跑）。
- **未实现（设计 §2 明确不在一期）**：企微机器人通知（C22）；紧急放行（J11）；单 DE 重试；
  「停止发布」（C16 里的停止动作）；审批 12h/24h 时效提醒；OA 工单存在性对接。
- **与 C20 的偏差**：自审批按「阻断并提示由他人审批」处理（40008），未做代理/上级自动转交
  （无代理表；台账 R33 记录该取舍）。
- **重跑后的再提交**：整单重跑会把变更项送回「待提交」，上一代准入快照只作历史、不沿用；
  页面必须仍给「提交生产发布」，否则失败单没有恢复路径。
- **单元锁的租期上限**：停在生产流程里的单会持续续租部署单元；暂停超过 168 小时（可配）后
  不再续租，四小时租约到期即可被新发布获取，原单再执行时提示重新发布。

### 5.7 回滚【一期】

**FR-RB-01 入口**：发布页「进入生产回滚」；全局「发布记录及回滚」。

**FR-RB-02 回滚选择**
- **当前线上版本**：代码库、分支模式、流水线模式、基线版本、发布单号、发布完成时间、发布人、成功发布的环境、更新内容。
- **近 10 个历史版本**单选。
- **必读提示**：
  - **一期只回滚镜像**：平台不自动回退代码；代码回退由团队在 CODING 侧手工处理（C25）。
  - **二期**：随写基线引入 revert MR 能力，届时可做到「镜像立即回 + 自动提 revert MR」。
  - 兼容（非标）流水线：**仅回滚镜像**，代码由团队自管。
  - 多单元共库：代码回退会影响共库的其他单元，需确认影响面。

**FR-RB-03 回滚执行与记录**
- **发起**：owner 或运维；**执行**：运维（生产环境）。测试/日常环境回滚由 owner 自助（J13）。
- **一期（C25）**：**镜像立即回滚** → 调 CODING 部署到历史版本镜像，分钟级止损；页面同时给出「代码回退需人工处理」的提示与目标 commit。
- **二期**：在镜像回滚之外自动创建 revert MR（原合并 commit 的反向变更），由 owner 合并。
- **免审批但强制填原因**；不受窗口约束；封板期提示但不阻断（J13）。
- 生成回滚单，记录发起人、执行人、目标版本、镜像回滚结果；「回滚任务列表」Tab 展示历史。

### 5.8 日常发布【一期，C10】

**FR-D-01 入口与范围**
- 变更项行「日常」按钮（二方库无此入口）。
- 走**简化流水线**：`构建（复用唯一构建任务）→ 日常部署（复用测试部署任务，或独立的日常部署任务）`；**无安全检查、无生产、无写基线**（C24）。
- 不占上线发布单号，不进回滚候选，不参与生产准入。
- **不占上线占用锁**，可多次并行；共用 CODING 构建并发槽。

**FR-D-02 日常环境**
- 部署单元下可配 N 个日常环境（原型「日常环境1/2」），每个环境若干 DE。
- 原型「日常发布校验」开关取消（日常环境本就不跑检查）。

**FR-D-03 日常发布记录**
- 记录：时间、分支、commit、执行人、结果、日志链接；供开发自查。

**FR-D-04 与上线的关系**
- 日常发布成功 ≠ 可上线；上线仍需完整走构建与测试部署（日常不复用镜像，J4）。

### 5.9 配置管理【二期】

- **FR-C-01 disconf / 应用配置**：disconf、nacos、apollo；按 DE 展示资源、类型、关联、操作「关联」「应用配置」；版本管理与下发联动流水线。
- **FR-C-02 部署配置（configmap）**：开关、按环境标签 + DE 配置、批量「部署配置发布」；生产/容灾/高峰**资源共用配置**。

- **发起人（C20）**：SQL/配置变更由**运维/运维组长**发起（开发亦可）；**发起人若已具备该类变更的审批权，免审批直接执行并留痕**。

### 5.10 CODING 对接【一期重点】

**FR-I-01 连接配置**
- 全局（或按系统/单元）：平台地址、团队/项目、访问凭证（加密、可轮换、失效告警）、**任务映射（单元 → 构建 / 测试部署 / 生产部署 / 日常部署 四类引用）**、部署目标映射（DE → CODING 部署环境参数）、制品库信息。
- **连接测试**：校验凭证、项目可达、构建计划存在。
- **实现（随 P2 之后落地）**：平台设置页「CODING 对接」维护一条全局连接（地址 / 团队 / 默认项目 / 凭证），
  「测试连接」用任务清单接口同时验证地址、凭证与项目，并回显构建/部署任务数；凭证加密、只回显前四位，
  留空即保留原值。系统级 `coding_project` 可覆盖默认项目，留空即继承。按系统/单元各配一条连接的覆盖
  不在本期（引擎当前只解析全局连接），记录为 P3 待办。

**FR-I-02 构建触发与状态回传**
- 按分支 + 构建参数触发；webhook 优先、轮询兜底；状态映射（排队/运行/成功/失败/取消）。
- 日志：跳转 CODING 或代理展示。

**FR-I-03 部署触发与状态回传**
- 触发部署到指定 DE；回传状态、耗时、失败原因；镜像/制品地址回写。

**FR-I-04 构建参数【一期不做，二期随自研构建引入】**

- 二期自研「分支管理 + 构建 + 打包 + 部署」时，按原型构建配置字段落地：工程类型（maven/gradle/npm/go/python…）、JDK/Node 版本、构建文件路径、构建命令、多线程构建、构建发布包路径与名称、Maven 版本、超时（默认 60 分钟）、构建节点、清空工作空间、上传子模块 jar，并按语言模板化（附录 B）。

**FR-I-05 凭证与安全**：不明文落库、不落日志、最小权限、留痕。

## 10. 一期 / 二期范围
