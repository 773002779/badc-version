### GAP-01 回滚（镜像回滚 + 记录 + 入口）——P0 · 已完成（P4-A）

- **需求**：FR-RB-01/02/03；C17（一期只回镜像，代码回退人工）、J13（免审批、强制原因、发起 owner/运维、执行运维、封板提示不阻断）；技术方案 §8.5。
- **现状**：已交付（2026-11-24）。接口四个：`GET /api/v1/units/{id}/rollback-versions`、`POST /api/v1/rollbacks`、`GET /api/v1/rollbacks`、`GET /api/v1/rollbacks/{id}`；回滚实例 `trigger_type=ROLLBACK`、只有 `PROD_DEPLOY` 一个节点、反向批次；V25 建 `rollback_record` 并给 `release_order` 加 `executed_by`；成功后来源变更项 `DONE → ROLLED_BACK`、发布单同步，变更项已不在 `DONE` 时只记成功。
- **证据**：`web/controller/RollbackController.java`、`application/{RollbackService,RollbackCompletionService}.java`、`infra/repo/RollbackRecordMapper.java`、`domain/pipeline/PipelineFactory.java#createRollback`、`server/src/main/resources/db/migration/V25__rollback.sql`；`server/src/test/java/com/sf/release/rollback/` 31 个测试；提交 `90d64da`（后端）、`8c2199b`（版本口径修正）、`980c87d`（发布详情返回 `unitId`）、`a6a631e`（前端）。实现落点与设计差异见技术方案 §8.7，接口见 §12.2.4。
- **验收口径**：
  1. `GET /api/v1/units/{id}/rollback-versions` 返回当前线上版本 + 近 10 个历史版本（来源：成功生产部署记录，含 release_order 发布单号、镜像 digest、完成时间、执行人、批次、环境）。
  2. `POST /api/v1/rollbacks`（unitId、目标版本 digest、原因）→ 创建 `ROLLBACK` 实例，仅 `PROD_DEPLOY` 节点，按**反向批次**（BLUE → DR → PROD）串行；复用单元锁；不占发布单号；写 `rollback_record`。
  3. `DONE` 的变更项经 `ROLLBACK` 变 `ROLLED_BACK`；发布单状态同步；已成功批次不回滚之外的批次不动。
  4. 必填原因；不校验窗口；封板期返回「提示但不阻断」标记；审计（P4-C 接入）。
  5. 页面：发布内容页常驻「进入生产回滚」；全局「发布记录及回滚」页（列表 + 回滚入口，同时满足 GAP-10）。
  6. 测试：状态机、批次顺序、锁冲突、原因必填、版本清单边界（0/1/10+ 条）。

### GAP-04 日常发布——P1 · 已完成（P5-A）

- **需求**：FR-D-01..04、C10/C24、J4。

  （`BUILD → DAILY_DEPLOY` 两节点）：构建复用单元唯一的 `BUILD` 任务链，部署节点为每个目标 DE 预生成一条

  缺失回退 `TEST_DEPLOY`（C24）。同一变更项可并行多次，无「已有运行中日常」检查；每次发起写一行
  `DAILY_START` 审计（对象 `ITEM`、`scope_unit_id`）。
- **证据**：`server/src/main/resources/db/migration/V28__daily.sql`（`pipeline_instance` 加
  `item_id/unit_id/requested_by` + `idx_instance_item`）；`domain/pipeline/PipelineFactory.java#createDaily`、
  `domain/pipeline/NodeType.java`（`DAILY_DEPLOY`）、`domain/pipeline/handler/DailyDeployNodeHandler.java`、
  `infra/repo/MybatisPipelineRepository.java#dailyBuildContextOf/#dailyDeployContextOf`、
  `infra/repo/DailyQueryMapper.java`、`application/DailyReleaseService.java`、
  `web/controller/DailyController.java`、`web/dto/DailyDtos.java`；
  `web/src/views/TaskDetailView.vue`、`web/src/api/{index,types}.ts`；
  `server/src/test/java/com/sf/release/daily/` 55 个测试（53 `@Test` + 2 `@ArchTest`），全量 802 绿；

  页面见前端设计 §15。
- **验收口径**：
  1. `POST /api/v1/items/{itemId}/daily` → `DAILY` 实例：构建（复用 BUILD 任务）→ 日常部署（节点
     `DAILY_DEPLOY`，任务 `DEPLOY`；`DAILY_DEPLOY` 绑定缺失回退 `TEST_DEPLOY`；无日常 DE 回退测试 DE）；

     `deploy_unit_lock=0`、`release_item.status` 不变）。

     日常仍可发起，且不释放在线实例的锁；构建并发仍由引擎侧限流（本切片不新增上限）。
  3. `GET /api/v1/daily/{pipelineNo}` 与日常记录列表（时间、分支、commit、执行人、结果、日志链接）。
     ——**已交付**：详情含两节点/任务与逐任务 `externalUrl`；记录列表按变更项分页，含时间/分支/commit/
     执行人/结果；**列表本身不含逐任务日志链接**（点行开抽屉看，见残留）。

  5. 测试：不占锁、不跑门禁、重复发起不互相阻塞、失败不影响上线流程。——**已交付**：另有事件隔离
     （日常事件不改 item、不写通知）、审计失败不阻断、handler 失败/回退/幂等重入等覆盖。
- **偏差/残留**：
  - **日常并行不分批**：部署节点一次触发全部目标 DE，失败也不回滚任何已部署 DE（记录里能看到哪些成功）。
  - **不做镜像一致性校验**：日常镜像不进入上线候选（J4），只要求实例有构建出的 `image_digest`。

    返回 null。

    未做日常环境配置页、日常镜像入库。

  4. 全部写审计与通知。

## 6. 风险与取舍（先写下来，避免实施时反复）

- **回滚的版本清单来源**：一期只能用「成功生产部署记录」推导（无制品库索引）；同一 digest 多次部署时取最近一次。若需要按版本号检索，需 Q4。
- **回滚与发布单**：回滚不新建发布单（J16 发布单号复用语义），单独 `rollback_record`；否则发布记录会被回滚刷屏。
- **P4-A 已交付后的残留（已接受）**：
  - 归属窗口：版本清单在取单元锁前读，两个并发回滚可能各自读到旧清单；单元锁保证串行执行，但「从哪个版本回滚」可能略早于真正取锁的时刻。
  - 批次数与环境是 digest 维度：同一 digest 被多次部署时，页面显示该 digest 全部成功生产部署的并集
  （`COUNT(DISTINCT node_task.batch_no)` 为批次数、环境按 `env_kind` 去重），不是某一次发布单的批次。
  - `rollback_record.created_at` 与 `release_order.created_at` 无索引（一期表小，深分页会 filesort）。
  - `keyword` 的 LIKE 不转义 `%` / `_`（与其他列表一致，包含匹配，不是注入风险）。
  - 全局页只列发布单，不含回滚记录行（回滚有独立接口 `GET /api/v1/rollbacks`，页面未列）。
  - 回滚只切镜像、不回退代码，页面固定提示人工 revert（C17；二期补 revert MR）。
- **通知的可靠性**：站内为权威记录，企微尽力而为（失败重试一次）；P4-B 已交付，下列残留均已接受。
- **P4-B 已交付后的残留（已接受）**：
  - **企微 at-least-once**：单实例按 id 取 `PENDING` 行、无分布式锁；多实例部署可能重复发送一次，
    失败重试后进程崩溃也可能重发，不追求 exactly-once。
  - **通知与业务事务非原子**：`notify` 用 `REQUIRES_NEW` 写库（提交失败也包在吞异常的 `try` 内），
    业务事务回滚的极端情况下仍可能留下一条通知；严格一致需 outbox + 提交后投递（P7）。
  - **封板影响面按通知时刻计算**：解除/到期按当时范围内在途单寻址，创建时的影响面没有落库快照，
    封板期内新提交的单由准入面板提示，不补发。
  - **webhook 单租户**：一个平台一条机器人地址（`notification_setting.id=1`）；按系统分机器人是二期。
  - **无保留期清理**：`notification`/`notification_setting` 本期不清理，保留策略随 P7 与审计一起定（Q6）。
  - **接收人不按 `user_scope` 过滤**：按平台角色（`user_role`/`role_permission`）解析，与审批「角色可签」
    一致；数据范围只约束业务访问，不约束通知。
  - **邮件/飞书未实现**：只留 `NotificationChannel` 枚举与 `NotificationSender` 接口（Q5 未定）。
  - **审批时效提醒未实现**：12h 提醒 / 24h 升级仍在 P7（GAP-12），本阶段只做事件通知。
  - **无失败重投队列**：一次重试后 `FAILED`，不自动再投；**企微失败行不在通知中心展示**——列表只查
    `channel='INAPP'`，设计 §1 的「运维可在通知中心看到失败行」未实现，`failure_reason` 要查
    `notification` 表或派发日志；越权标他人行回 40000（HTTP 200），不是设计 §8 的 403/404。
  - **读侧轮询**：徽标 30s 轮询 + 路由刷新，不是服务端推送。
- **审计的写入位置**：在应用服务内同步写，不依赖 AOP 猜测；失败不回滚业务（写审计失败只记 ERROR），避免审计成为业务故障点。
- **P4-C 已交付后的残留（已接受）**：
  - **审计与业务非原子**：`AuditService.record` 用 `REQUIRES_NEW` 独立事务（提交失败也包在吞异常的
    `try` 内），业务事务回滚的极端情况下仍可能留下一条「未发生」的审计；严格一致需 outbox（P7）。
  - **before/after 只是字段子集**：只存触发点给的变化字段，不是整行快照；查「当时完整状态」要结合
    业务历史表；个别 update 只覆盖身份/状态/关键配置字段。
  - **平台级行仅全量范围可见**：通知设置等平台级行（两个 scope 列皆空）只有 `ALL` 范围能读；
    系统级设置行（CODING SUBSYSTEM、窗口 SUBSYSTEM）按 `scope_subsystem_id` 收敛。
  - **无保留期清理**：`audit_log` 本期只追加、不清理，没有归档表与审计告警（P7，Q6）。
  - **动作仍随 P5/P6 接**：日常发布的 `DAILY_START` 已随 P5-A 接线（对象 `ITEM`、`scope_unit_id`）；
    关闭/退出/归档、强拆锁的动作仍只有枚举占位，无触发点、不写行（GAP-05）；**紧急放行没有枚举占位**，
    GAP-11 落地时需新增动作码（不改表结构）。
  - **越界 `unitId` 回空页**：审计不暴露单元是否存在（与发布记录页的 40009 刻意不同）；无单元范围的
    调用者看到空页/仅表头 CSV，不报错。
  - **导出是同步 5000 行上限**：超出截断并在末行提示，没有后台导出任务；导出动作本身不写审计行。
  - **复核与执行尝试未留痕**：技术方案 §8.4 的两条承诺（「复核结果写 `audit_log`」「`execute_attempt`
    留痕」）未实现——`ReviewService` 只读，没有复核审计动作，也没有 `execute_attempt` 表；执行只有
    `EXECUTE_PROD` 一行，复核结论（封板/镜像/豁免）只在接口响应与拒绝错误码里。
  - **日期范围未进前端探针**：`from`/`to` 已接且有 40000 校验，但 `verify-p4c-ui.mjs` 只覆盖动作/
    对象类型/对象 ID 三条筛选路径（双月面板的确定性点击成本高），属已知测试缺口。
- **P5-A 已交付后的残留（已接受）**：
  - **日常并行不分批**：部署节点一次触发全部目标 DE，失败不回滚任何已部署的 DE；不设并行上限，同一
    变更项可无限次同时发起（构建并发仍由引擎侧限流）。
  - **不做镜像一致性校验**：日常镜像不进入上线候选（J4），只要求实例有构建出的 `image_digest`；也不做
    日常镜像入库。
  - **不写通知**：FR-N-01 未列日常，只写 `DAILY_START` 审计；`PipelineEventListener` 对 `DAILY_DEPLOY`
    节点与日常实例显式返回 null。
  - **日常 DE 变更后实例不重算**：创建后改目标 DE/绑定，旧实例任务以 `DE_NOT_CONFIGURED` /
    `UNIT_NOT_CONFIGURED` 显式失败（`result_summary`），节点/实例 FAILED，不静默也不重算。
  - **记录列表不含任务级日志链接**：`GET /api/v1/items/{itemId}/daily` 只回实例行；逐任务 `externalUrl`
    在详情抽屉里（列表的「日志」列是「查看」入口）。
  - **目标环境不在接口/按钮旁返回**：POST 只回 `{pipelineNo, instanceId}`，确认框用固定文案说明
    「优先日常 DE、回退测试 DE」；设计 §6 允许的两种提示都未实现。
  - **真实 CODING 成功路径未验证**：本机无连接，真实记录以 `ENGINE_UNAVAILABLE` 失败；成功路径只有
    fake engine 单测。UI 证据来自种子 `PL-DEMO-DAILY-*` + live 后端。
- **stop 与 exit 的语义边界**：stop = 不跑后续批次（实例 TERMINATED，已上线不动）；exit = 放弃整条流程（级联关闭变更项）；close = 变更项级终止；archive = 任务级只读。
- **非功能**：50 并发与 99.9% 需要环境与 Q6，先做可在本地验证的部分（首屏、接口耗时、N+1、索引），压测单独排期。
