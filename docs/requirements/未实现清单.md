## 1. 一期缺口（有需求、无入口）

> GAP-01 与 GAP-10 已随 P4-A 交付，保留在原处以期验收留痕（标题标 · 已完成）；本节其余条目仍是缺口。

### GAP-01 回滚（镜像回滚 + 记录 + 入口）——P0 · 已完成（P4-A）

- **需求**：FR-RB-01/02/03；C17（一期只回镜像，代码回退人工）、J13（免审批、强制原因、发起 owner/运维、执行运维、封板提示不阻断）；技术方案 §8.5。
- **现状**：已交付（2026-11-24）。接口四个：`GET /api/v1/units/{id}/rollback-versions`、`POST /api/v1/rollbacks`、`GET /api/v1/rollbacks`、`GET /api/v1/rollbacks/{id}`；回滚实例 `trigger_type=ROLLBACK`、只有 `PROD_DEPLOY` 一个节点、反向批次；V25 建 `rollback_record` 并给 `release_order` 加 `executed_by`；成功后来源变更项 `DONE → ROLLED_BACK`、发布单同步，变更项已不在 `DONE` 时只记成功。
- **证据**：`web/controller/RollbackController.java`、`application/{RollbackService,RollbackCompletionService}.java`、`infra/repo/RollbackRecordMapper.java`、`domain/pipeline/PipelineFactory.java#createRollback`、`server/src/main/resources/db/migration/V25__rollback.sql`；`server/src/test/java/com/sf/release/rollback/` 31 个测试；提交 `90d64da`（后端）、`8c2199b`（版本口径修正）、`980c87d`（发布详情返回 `unitId`）、`a6a631e`（前端）。实现落点与设计差异见技术方案 §8.7，接口见 §12.2.4。
- **验收口径**：
  1. `GET /api/v1/units/{id}/rollback-versions` 返回当前线上版本 + 近 10 个历史版本（来源：成功生产部署记录，含 release_order 发布单号、镜像 digest、完成时间、执行人、批次、环境）。
  2. `POST /api/v1/rollbacks`（unitId、目标版本 digest、原因）→ 创建 `ROLLBACK` 实例，仅 `PROD_DEPLOY` 节点，按**反向批次**（BLUE → DR → PROD）串行；复用单元锁；不占发布单号；写 `rollback_record`。
  3. `DONE` 的变更项经 `ROLLBACK` 变 `ROLLED_BACK`；发布单状态同步；已成功批次不回滚之外的批次不动。
  4. 必填原因；不校验窗口；封板期返回「提示但不阻断」标记；审计（P4-C 接入）。
  5. 页面：发布内容页常驻「进入生产回滚」；全局「发布记录及回滚」页（列表 + 回滚入口，同时满足 GAP-10）。
  6. 测试：状态机、批次顺序、锁冲突、原因必填、版本清单边界（0/1/10+ 条）。

### GAP-02 通知（站内 + 企微）——P0

- **需求**：FR-N-01；C22（封板强通知按产品/研发/测试/运维寻址，缺失兜底系统负责人）。
- **现状**：无通知表、无发送器、无接收人配置；只有事件总线与注释。
- **证据**：`application/event/PipelineEventListener.java` 仅做状态与账本；`grep Notification` 无实现类。
- **验收口径**：
  1. `notification` 表（id、事件、对象、接收人、渠道、状态、创建/发送时间、失败原因）；站内列表 `GET /api/v1/notifications` 与未读数。
  2. 事件至少覆盖：构建失败、部署失败、检查不通过、测试部署就绪、待审批、审批结果、门禁失效（生产中）、生产完成、豁免待审、回滚完成、封板生效/解除、锁超时释放。
  3. 封板事件按任务成员角色（产品/研发/测试/运维）解析接收人，缺失回落到系统负责人；一次事件去重。
  4. 企微机器人：webhook 地址可配（设置页），失败重试一次并记录失败原因，**不阻塞主流程**。
  5. 邮件/飞书只留接口，不实现（Q5 未定）。
  6. 测试：接收人解析（含兜底）、去重、发送失败不影响流水线、开关关闭时不发。

### GAP-03 审计日志——P0

- **需求**：FR-N-02（谁在何时对哪个对象做了什么；可检索、可导出）。
- **现状**：无 `audit_log` 表、无查询/导出接口；现只有 `log.info` 与审批步骤、准入快照证据。
- **证据**：`resources/db/migration` 无 audit 表；`web/controller` 无审计端点。
- **验收口径**：
  1. `audit_log` 表：actor、action、object_type、object_id、before/after（JSON）、reason、trace_id、created_at；按对象与时间索引。
  2. 写入覆盖：发布、重跑、日常、豁免申请/审批、测试通过/撤回、检查刷新、生产提交/审批/驳回/执行、封板/解除、回滚、关闭/退出/归档、强拆锁、设置修改。
  3. `GET /api/v1/audit`（对象、动作、人、时间范围、分页）+ `GET /api/v1/audit/export`（CSV）。
  4. 页面：单元详情「操作日志」Tab + 全局审计页（可筛选）。
  5. 测试：动作留痕率（上述动作 100% 有记录）、查询过滤、导出内容。

### GAP-04 日常发布——P1

- **需求**：FR-D-01..04、C10/C24、J4。
- **现状**：`ExecType.DAILY`、`EnvKind.DAILY`、`TaskKind.DAILY_DEPLOY` 三个模型点存在，但没有创建路径；`PipelineFactory` 注释写明「daily pipeline 是后续任务」。
- **证据**：`grep ExecType.DAILY` 无调用；无 `/daily` 端点；无日常页面。
- **验收口径**：
  1. `POST /api/v1/items/{itemId}/daily` → `DAILY` 实例：构建（复用 BUILD 任务）→ 日常部署（`DAILY_DEPLOY`，为空则 `TEST_DEPLOY` 指向日常 DE）；**不建发布单、不占单元锁、不跑检查、不改变更项状态**。
  2. 可多次并行；共库共享构建并发。
  3. `GET /api/v1/daily/{pipelineNo}` 与日常记录列表（时间、分支、commit、执行人、结果、日志链接）。
  4. 页面：变更项行「日常」按钮 + 日常发布页（环境与记录）。
  5. 测试：不占锁、不跑门禁、重复发起不互相阻塞、失败不影响上线流程。

### GAP-05 停止 / 退出 / 关闭 / 归档——P1

- **需求**：FR-P-07（停止、退出流水线）、C16 的「停止」、FR-T-02「关闭」、FR-T-05（退出任务/归档，级联见 §4.8）。
- **现状**：只有批次边界「暂停 + 继续」；`ItemEvent.CLOSE/EXIT`、`TaskStatus.ARCHIVED` 只在枚举与状态机中，无服务/端点/UI。
- **证据**：`ReleaseController` 只有 `GET detail`、`GET records`、`POST resume`；`TaskController` 无归档；`grep ItemEvent.CLOSE` 只命中状态机。
- **验收口径**：
  1. `POST /api/v1/releases/{publishNo}/stop`（原因）→ 取消后续批次（引擎任务 best-effort cancel），实例 `TERMINATED`，变更项 `EXIT → TERMINATED`；已上线批次不回滚；释放单元锁。
  2. `POST /api/v1/releases/{publishNo}/exit`（原因）→ 终止实例（含 PAUSED），级联见需求 §4.8；锁释放；二次确认。
  3. `POST /api/v1/items/{itemId}/close`（原因）→ `CLOSED`；`POST /api/v1/tasks/{id}/archive` → 任务只读、变更项级联关闭、记录保留。
  4. 全部写审计与通知。
  5. 页面：节点任务「停止发布」、页头「退出流水线」、变更项「关闭」、任务「归档」。
  6. 测试：四个状态的合法/非法路径、锁释放、级联规则、重复调用幂等。

### GAP-06 待办中心——P1

- **需求**：FR-N-03；页面 IA #11「审批待办」。
- **现状**：无 `/todos`、无页面；审批、执行、测试只能从各自发布页进入。
- **验收口径**：
  1. `GET /api/v1/todos` 返回「我的待测试」「我的审批」「待我执行」「我发起的」四组及计数，数据来自现有状态与角色（PENDING_APPROVAL + 步骤角色、READY + 运维、GATE_PENDING + 测试成员、我创建的任务）。
  2. 每项带对象、状态、等待时长、直达链接。
  3. 页面 `/todos`（四段列表 + 计数徽标），导航「待办」。
  4. 测试：四种角色的可见集合、越权不可见、空态。

### GAP-07 二方库制品与发布流水线——P2

- **需求**：FR-R-03（制品坐标、版本规则、依赖影响面）、FR-P-09（二方库流水线）、C13（先检测后入库）。
- **现状**：单元/变更项 `type=LIB` 可建可查；发布直接拒绝「二方库发布流水线不在本期范围」（`PublishAppService.java`）。无制品库模型。
- **验收口径**：
  1. 单元增加制品坐标（groupId/artifactId）、版本规则；`GET /api/v1/libs/{id}/dependents` 返回依赖它的单元。
  2. LIB 流水线：构建 → 检测 → 入库（引擎入库任务）；成功即 `DONE`（FR-T-04 口径）；不进入生产准入。
  3. 制品库归属按 Q4 结论接入；未定时只落库坐标与入库任务，不接具体私服。
  4. 页面：二方库详情（制品、依赖、发布记录）。
  5. 测试：发布路径、完成率计入、依赖查询、产物缺失拒绝。

### GAP-08 平台设置补齐——P2

  2. `GET/PUT /api/v1/settings/{section}` + 设置页分区；改动即时生效或明确重启提示。
  3. 权限：`setting:manage`；审计每次修改。
  4. 测试：默认值、校验、生效、越权。

## 6. 风险与取舍（先写下来，避免实施时反复）

- **回滚的版本清单来源**：一期只能用「成功生产部署记录」推导（无制品库索引）；同一 digest 多次部署时取最近一次。若需要按版本号检索，需 Q4。
- **回滚与发布单**：回滚不新建发布单（J16 发布单号复用语义），单独 `rollback_record`；否则发布记录会被回滚刷屏。
- **P4-A 已交付后的残留（已接受）**：
  - 归属窗口：版本清单在取单元锁前读，两个并发回滚可能各自读到旧清单；单元锁保证串行执行，但「从哪个版本回滚」可能略早于真正取锁的时刻。
  - 批次数与环境是 digest 维度：同一 digest 被多次部署时，页面显示该 digest 全部成功生产部署的并集（`COUNT(DISTINCT node_task.target_id)`），不是某一次发布单的批次。
  - `rollback_record.created_at` 与 `release_order.created_at` 无索引（一期表小，深分页会 filesort）。
  - `keyword` 的 LIKE 不转义 `%` / `_`（与其他列表一致，包含匹配，不是注入风险）。
  - 全局页只列发布单，不含回滚记录行（回滚有独立接口 `GET /api/v1/rollbacks`，页面未列）。
  - 回滚只切镜像、不回退代码，页面固定提示人工 revert（C17；二期补 revert MR）。
- **通知的可靠性**：站内为权威记录，企微尽力而为（失败重试一次）；封板强通知若 Q5 未定，先落站内 + 邮件接口占位。
- **审计的写入位置**：在应用服务内同步写，不依赖 AOP 猜测；失败不回滚业务（写审计失败只记 ERROR），避免审计成为业务故障点。
- **stop 与 exit 的语义边界**：stop = 不跑后续批次（实例 TERMINATED，已上线不动）；exit = 放弃整条流程（级联关闭变更项）；close = 变更项级终止；archive = 任务级只读。
- **非功能**：50 并发与 99.9% 需要环境与 Q6，先做可在本地验证的部分（首屏、接口耗时、N+1、索引），压测单独排期。
